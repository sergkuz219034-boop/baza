# Воркеры и расписание

## Подтверждено

- отдельный контейнер `traffichub_worker`
- модель исполнения: subprocess-per-owner
- default live parallel owners: `2`
- heartbeat file:
  - `/app/data/runtime/worker.heartbeat`
- worker healthcheck считает контейнер healthy, если heartbeat-файл моложе `180` секунд
- live web-layer отдельно крутит hourly `partner_sync` loop в `autolead_server_bot`, а не в `traffichub_worker`

## Scheduler / loops

- background loops живут не только в worker, но и в web-layer;
- `api/server.py` создаёт `partner_sync_task` через lifespan;
- scheduler enqueue boundary живёт в `services/leads_service.py::run_server_mode()`, а не в `traffic_hub/worker.py`;
- с `2026-06-21` один scheduler tick fan-out'ит `run` по всем `schedulable owners`, а не только по одному `autolead_owner`;
- с `2026-06-26` расписание opt-in: дефолт `schedule_enabled=false`, пустой или отсутствующий флаг не запускает scheduler;
- UI также должен показывать toggle расписания выключенным, если `schedule_enabled` не равен `true`;
- live log подтверждал hourly `partner_sync` для `audit-admin`:
  - `2026-06-17 00:27:33`
  - `2026-06-17 01:27:33`

## Что важно для дебага

- зависание одного owner-job может менять общую картину исполнения;
- если scheduler срабатывает, но запускается только один пользователь, проверять `control_license_users`, `control_user_app_configs`, `control_user_app_auth` и helper `_iter_schedulable_owners()`;
- если scheduler срабатывает неожиданно у нового пользователя, первый check — явно ли у него сохранён `schedule_enabled=true`;
- проверять надо не только очереди, но и heartbeat, parallel owner limit и runtime log feed;
- scheduler и worker нельзя описывать как один фоновой цикл: это набор разных execution paths;
- если пропал `partner_sync`, смотреть сначала web-container `autolead_server_bot`, а не worker logs.

## Главные вопросы при расследовании

- job вообще был поставлен в очередь или потерялся раньше;
- worker поднят и пишет heartbeat;
- owner-context не сериализует весь контур сильнее, чем ожидалось;
- fan-out по owner'ам происходит до worker, на этапе enqueue;
- UI получает финальный runtime state, а не устаревший snapshot.

## Owner-scoped расписание Autolead

- `schedule_enabled` и `schedule_times` хранятся отдельно по `control_user_app_configs.login`.
- Scheduler не должен использовать один общий список времён для всех users.
- Runtime строит план `time -> owners`: в конкретное время запускаются только owner'ы, у которых это время сохранено и включено.
- Если `schedule_enabled=false`, пустой или отсутствует, owner не попадает в план.
- Если `schedule_times=[]`, owner не попадает в план даже при `schedule_enabled=true`.
- Regression tests: `tests/test_scheduler_config.py`.
- Расследование: [[03_Ошибки/Расследования/2026-06-27 Owner-scoped Autolead schedule]].
