# Бэкенд

## AccountManager scheduler datetime contract

- `AccountManager/scheduler.py` работает с PostgreSQL `DateTime(timezone=True)` полями.
- Все текущие сравнения времени в scheduler должны идти через timezone-aware UTC:
  - `_utc_now()`;
  - `_as_utc(value)`.
- Не использовать `datetime.utcnow()` в scheduler: это создаёт naive datetime и ломает сравнение с aware DB timestamps.
- Regression test: `tests/test_account_manager_scheduler_timezones.py`.

## Типовой маршрут чтения кода

1. Найти внешний симптом: endpoint, page action, ws-event или background job.
2. Определить entrypoint в `api/*` или `traffic_hub/*`.
3. Проследить переход в service/repository слой.
4. Проверить, где появляется owner-context и где он может потеряться.
5. Сверить код с runtime-фактами: логи, heartbeat, storage artefacts, DB rows.

## Частые ловушки

- считать `services/*` и `modules/*` второстепенными, хотя они участвуют в live-path;
- игнорировать `AccountManager/*` как будто это отдельный “вспомогательный” проект: для `content bot`, Telegram/Google/Social account flows и их dashboard это live entrypoint;
- смотреть только web-router и не доходить до worker/runtime;
- перепутать control-конфиг и runtime-состояние.
- трактовать наличие `sqlite3`-импортов как доказательство, что active runtime всё ещё работает на SQLite;
- смешивать `utils/database.py` runtime facade, `utils/runtime_repository.py` read model и `utils/control_store.py` control contour в одну и ту же storage-зону.

## AccountManager content contour

- `AccountManager/api/routers/content.py` — канонический API-layer для content sources, posting targets, posting tasks, content settings и `content bot` endpoints.
- `AccountManager/services/content_bot_service.py` — bot-config, default-target sync, OpenRouter generation и Telegram Bot API publish path.
- `AccountManager/dashboard/index.html` + `AccountManager/dashboard/app.js` — live dashboard для content pipeline и `content bot`.
- для этого контура важна idempotency boundary:
  - повторный create/update не должен плодить duplicate `PostingTarget`;
  - повторный queue/approve не должен плодить duplicate open `PostingTask`;
  - `default_target_id` должен синхронизироваться через bot config, а не жить отдельной “скрытой” логикой UI.

## Storage boundary

- `utils/database.py` — runtime facade с PostgreSQL-first routing и SQLite fallback;
- `utils/runtime_repository.py` — read model для owner leads/history/summary, уже умеет PostgreSQL path;
- `utils/control_store.py` — отдельный control-store/hybrid слой с собственным `control.db` и legacy import path;
- `services/stats_service.py` пока ещё имеет SQLite-oriented ветку для части метрик и не должен автоматически считаться признаком rollback всего runtime.

## Tenant и owner boundary

- live PostgreSQL уже требует `tenant_id NOT NULL` для tenant-scoped `traffic_hub` таблиц;
- при создании `PostbackLog`, `Lead`, `Conversion`, `Payout`, `FinancialRecord`, `Offer`, `Funnel`, `MessengerAccount`, `NetworkIntegration`, `NetworkOfferStat` код обязан явно передавать tenant context;
- `traffic_hub/api/routers/postbacks.py::_handle_postback` является примером корректной записи `PostbackLog` с `tenant_id` и `owner_username`;
- `traffic_hub/api/routers/integrations.py::_import_network_conversions` на 2026-06-24 проверен: `PostbackLog` создаётся с `tenant_id` и `owner_username`;
- `traffic_hub/api/routers/funnels.py::create_funnel` и `traffic_hub/api/routers/tracking.py::track_offer_click` на 2026-06-24 исправлены после падения tenant-isolation tests;
- не доверять `nullable=True` в `traffic_hub/models/database.py` без сверки с migrations/live DB.

## Full-cycle boundary

- `services/leads_service.py:run_full_cycle()` — основной путь: сбор лидов, выгрузка в основную Google Sheets таблицу, чтение строк основной таблицы для отправки, отправка через `modules/vbiv_bot.py`, запись в отработанную таблицу и обратная маркировка основной таблицы.
- `api/routers/leads.py:POST /api/leads` — ручное добавление лида в owner-scoped базу Autolead. Поддержанные поля: `ФИО`, `Пол`, `Вакансия`, `Дата`, `Номер`, `Почта`, `Город`, `Возраст`, `Резюме`. Endpoint требует `require_autolead_access`, сохраняет лид через `utils.database.save_leads()` в контексте текущего пользователя и пытается сразу выгрузить строку в Google Sheets через `services.leads_service.upload_sheets()`. Источник фиксируется как `_source_type=manual`.
- Runtime storage для ручных лидов расширен в обоих контурах: `utils/runtime_store_pg_leads.py` и SQLite fallback `utils/runtime_store_schema.py` / `utils/runtime_store_leads.py` хранят `email`, `age`, `birth_date`, `resume_url`. Это нужно для SaaS и локальной скачиваемой версии.
- `modules/vbiv_bot.py:run_campaign()` обязан возвращать `lead_results` для каждого лида, по которому есть итоговый статус, включая ошибки, отсутствие подходящего оффера, лимиты и `already_sent`.
- `modules/platforms/base.py::_wait_success()` не должен считать обычный URL-редирект доказательством отправки анкеты. Success разрешён только по явному success selector/body/modal/dialog или URL marker `success/thanks/submitted/confirmed`. Это защищает от ложных `sent` в `autolead_send_history`.
- Browser/form proxy boundary: если `_playwright_proxy_from_config()` вернул proxy из включённых настроек пользователя, Playwright-заполнение должно использовать его для всех офферов. Allowlist доменов для proxy запрещён, потому что новые офферы иначе уходят с IP сервера. Расследование: [[03_Ошибки/Отладка/Решённые баги/БАГ-037_form_proxy_all_browser_offers]].
- `modules/sheets_sync.py:mark_pending_leads_processed()` является каноничной точкой фиксации статуса строки в основной таблице; `pending` здесь только внутреннее имя в коде.
- `modules/sheets_sync.py` может использовать bulk update/write path, но обязан сохранять fallback на старый worksheet API для тестовых fake-объектов и совместимости.
- История отправок owner-scoped: ключ должен формироваться через `utils.database._compose_history_key()` в формате `owner:phone:offer`. Ручное сравнение `phone:offer` устарело.
- расследование: [[03_Ошибки/Отладка/Решённые баги/БАГ-002_full-cycle_admin_statuses]]

## Partner conversions boundary

- Для бизнес-метрик TrafficHub `payout > 0` является финансовым источником истины.
- Если ПП возвращает raw status `rejected`, но `payout > 0`, TrafficHub классифицирует событие как `ConversionStatus.approved`, сохраняя raw payload в `Conversion.raw_data` / `PostbackLog.raw_data`.
- `traffic_hub/api/routers/postbacks.py::_mark_autolead_pending_from_postback()` обязан загружать Google Sheets config через owner-context интеграции, а не через глобальный `load_config()`.
- расследование: [[03_Ошибки/Отладка/Решённые баги/БАГ-036_false_form_success_lovko_pp_conversions]]

## Zarplata.ru API boundary

- Источник подтверждения: официальный OpenAPI `https://api.zarplata.ru/openapi/redoc` / `https://api.zarplata.ru/openapi/specification/zarplata`.
- Импорт резюме использует `GET /resumes` с пагинацией `page`, `pages`, `per_page`; максимальный `per_page` для `/resumes` по spec — `100`.
- `/resumes` имеет depth limit 2000 элементов: при `per_page=100` безопасны только страницы `0..19`. Код не должен запрашивать страницу `20`, даже если API вернул `pages > 20`.
- `GET /resumes` сам по себе не является полным контуром всех лидов работодателя: отклики/приглашения нужно добирать через `only_in_responses=true` и `GET /negotiations` collections.
- До первого фикса `modules/zarplata_api.py::import_resumes()` брал только первую страницу, из-за чего собирались не все лиды.
- После первого фикса `ZarplataClient.search_all_resumes()` проходит все страницы и возвращает `pages_loaded`.
- После повторного фикса 2026-06-30 `import_resumes()` объединяет обычный поиск, поиск только по откликам/приглашениям и `item.resume` из collection items `/negotiations`; collection-запросы не фильтруются `status=active`, чтобы не терять неактивные коллекции.
- Если общий `/resumes` поиск обрезан лимитом 2000, результат помечается `truncated_by_api_limit=true`, но импорт продолжает `/negotiations` и не валит полный цикл.
- Для долгих проходов `import_resumes()` обязан писать stdout-progress по этапам Зарплата.ру, иначе dashboard выглядит зависшим при рабочем API-обходе.
- Вакансии Zarplata.ru для вкладки `Вакансии` берутся через `GET /employers/{employer_id}/vacancies/active`; `employer_id` определяется из `/me`, поле `employer.id`.
- Product commits: `4362d77a4`, `e9a5e7c85`, `860adb539`.

## Playwright test isolation boundary

- `tests/test_lovko_scraper.py` не должен безусловно подменять `sys.modules["playwright"]`.
- Причина: после такого stub соседние тесты `modules/vbiv_bot.py` импортируют `playwright.sync_api` и получают ошибку `'playwright' is not a package`.
- Каноничный подход: если Playwright установлен в окружении, тесты используют настоящий пакет; stub допустим только при полном отсутствии зависимости и должен быть package-like module с `__path__`.
- Regression check: совместный запуск `tests/test_lovko_scraper.py tests/test_vbiv_bot_navigation.py tests/test_vbiv_bot_runtime_errors.py`.
- Fixed commit: `7608c0c8e`.

## Worker и web-loop boundary

- `traffic_hub/worker.py` пишет heartbeat в `WORKER_HEARTBEAT_FILE`, по умолчанию `/app/data/runtime/worker.heartbeat`;
- `run_worker()` пишет состояния `starting`, `alive`, `stopping`, `stopped`;
- `WORKER_MAX_PARALLEL_OWNERS` читается из env прямо в `traffic_hub/worker.py`;
- scheduler ставит owner-scoped `run` jobs через `services/leads_service.py::run_server_mode()` и helper `_iter_schedulable_owners()`;
- критерий `schedulable owner` сейчас подтверждён кодом:
  - активный пользователь в `control_license_users`;
  - есть запись в `control_user_app_configs`;
  - есть запись в `control_user_app_auth`;
  - effective owner-config даёт активный runtime-path (`rabota_ru` / `offer_mapping` / `google_sheets.enabled`);
- `partner_sync` живёт не в worker, а в `api/server.py`:
  - `_run_partner_sync_cycle()`
  - `_partner_sync_loop()`
  - `partner_sync_task = asyncio.create_task(_partner_sync_loop())` внутри lifespan.
- расследование: [[04_План/Материалы/сырьё/документы/TrafficHub-obsidian/01 Расследования/2026-06-17 Worker heartbeat и web-layer partner_sync]]
- расследование по scheduler fan-out: [[03_Ошибки/Отладка/Решённые баги/БАГ-030_scheduler_single_owner_run]]
