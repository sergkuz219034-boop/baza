# Тестовые данные

## Что важно

- owner/user данные не должны смешиваться;
- runtime secrets и service account files могут быть user-scoped;
- тестовые данные нужно отделять от live owner artifacts.
- временные SQLite-файлы и `sqlite+aiosqlite` engines в тестах — это fixture-механизм, а не описание текущего продового backend'а.

## Подтверждённые patterns

- tenant/auth tests создают isolated sqlite fixtures вида `traffic-auth.sqlite3`, `traffic-tenant-routes.sqlite3`;
- backup/import tests поднимают временные каталоги `tmp_path/backups` и `tmp_path/data/backups`;
- secrets/import tests используют fixture files вроде `service_account.json`, `rabota_tokens.json`;
- worker/ws tests часто работают на fake process / fake websocket объектах, а не на полном runtime.

## Практический вывод

- если баг требует live container, не пытаться “доказать” его только unit-test fixture;
- если баг чисто в owner-scope, auth, import backup или ws-manager semantics, локальный isolated test обычно достаточен.
