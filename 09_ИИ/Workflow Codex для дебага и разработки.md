# Workflow Codex для дебага и разработки

Канонический workflow для работы Codex с `TrafficHub`.

Цель: новый чат или новый разработчик не должен спрашивать, как подключаться, где канон и что проверять первым. Агент обязан идти по этому маршруту, пока не найден реальный блокер.

## Принципы

- Не спрашивать пользователя о подключении, каноне wiki или основном repo, пока не проверены `[[05_Эксплуатация/Доступ и подключения]]` и текущий workspace.
- Источник истины по продукту: код, runtime, БД, env, контейнеры, логи, серверные артефакты.
- Источник истины по знаниям: локальная wiki `wiki` и GitHub `sergkuz219034-boop/baza`.
- `/app` внутри контейнера не является каноническим repo. Это runtime-слой для проверки фактов.
- `/root/TrafficHub` на сервере является live host-repo для deploy, но не является wiki.
- Любой фикс считается завершённым только после проверки: локальный diff, commit, push, GitHub checks, live deploy при необходимости, runtime health, запись в wiki при наличии нового знания.

## Быстрый маршрут

1. Определить тип задачи: UI, API, worker, auth, deploy, БД, интеграция, wiki, GitHub checks.
2. Прочитать релевантные страницы wiki до правки кода.
3. Проверить код и runtime-факты, не доверять старым заметкам без подтверждения.
4. Воспроизвести симптом на минимальном контуре: `admin` и `artem`, если пользователь не указал других.
5. Исправить первопричину, а не симптом в UI.
6. Проверить, что фикс действует для всех users/owners, а не только для `admin`.
7. Запушить в GitHub и дождаться успешных checks.
8. Деплоить live только из `/root/TrafficHub`, подтянутого с `origin/main`.
9. Проверить live health и наличие нужного кода внутри контейнера `/app`.
10. Обновить wiki и синхронизировать `baza`.

## Обязательный порядок при live/runtime задаче

1. Прочитать `[[05_Эксплуатация/Доступ и подключения]]`.
2. Подключаться только через SSH alias `traffichub-live`.
3. Для сложных live-команд использовать PowerShell-safe wrapper `scripts/ssh_live_bash.ps1`.
4. На сервере первым делом выполнить:
   - `whoami`
   - `cd /root/TrafficHub`
   - `git remote -v`
   - `git status -sb`
   - `git rev-parse --short=9 HEAD`
5. Проверить, что `/root/TrafficHub` синхронизирован с `origin/main`.
6. Пересобрать и перезапустить нужный сервис через `docker compose`.
7. Проверить `docker compose ps`, `/api/health` или публичный health endpoint.
8. Проверить, что нужные строки/файлы есть внутри контейнера `/app`, если фикс frontend/backend должен попасть в image.

## Обязательный порядок при баге

1. Зафиксировать симптом: кто, где, что нажал, какой лог, какой screenshot.
2. Найти похожее в:
   - `[[06_Отладка/Каталог ошибок]]`
   - `[[06_Отладка/Воркараунды]]`
   - `[[06_Отладка/Активные баги/README]]`
   - `[[06_Отладка/Решённые баги/README]]`
3. Определить зону:
   - frontend state
   - backend API
   - auth/session
   - owner/user isolation
   - Google Sheets
   - Rabota.ru API
   - offer form automation
   - worker/scheduler
   - deploy/container drift
4. Проверить факты в коде и runtime.
5. Написать минимальный фикс.
6. Проверить регрессионные инварианты.
7. Если баг повторяемый или нетривиальный, создать/обновить заметку в `06_Отладка`.

## Инварианты, которые проверять почти всегда

- `admin` не должен быть единственным рабочим пользователем.
- Настройки Google Sheets, Rabota.ru API, offers, service account и runtime profile должны быть owner-scoped.
- Пользователь не должен видеть или использовать чужие настройки.
- Новые пользователи не должны наследовать мусорные admin defaults.
- Уже обработанные лиды не должны повторно отрабатываться.
- Ошибки формы оффера не должны ломать весь цикл.
- Account Manager доступен только admin.
- Maintenance mode виден users, но не должен блокировать admins.
- Live container `/app` должен соответствовать `origin/main`, а не старому mutable слою.
- GitHub checks должны быть зелёными после push.

## Стандарт фикса

Перед commit:

- `git status -sb`
- `git diff --check`
- релевантный тест или runtime probe

После push:

- проверить GitHub Actions;
- если checks красные, изучить логи, исправить причину и пушить новый commit;
- не говорить пользователю "готово", пока push/checks не подтверждены или блокер не описан конкретно.

При deploy:

- обновлять server repo из `origin/main`;
- не считать контейнер `/app` repo-источником;
- после deploy проверять health;
- если SSH оборвался во время build, перепроверить контейнер отдельной командой.

## Стандарт wiki

Если в ходе работы найдено новое знание:

1. Обновить точную страницу, а не писать дубликаты.
2. Для расследования использовать структуру:
   - Симптом
   - Зона системы
   - Гипотеза
   - Проверка
   - Наблюдение
   - Вывод
   - Следующий шаг
3. Помечать гипотезы как гипотезы.
4. Ссылаться на конкретный файл, endpoint, таблицу, env, контейнер или commit.
5. В конце синхронизировать локальную wiki с `sergkuz219034-boop/baza`.

## Как отвечать пользователю

- Коротко сообщать текущий шаг и факт, который проверяется.
- Не задавать вопросы, если можно проверить самому.
- Если нужен вопрос, сначала перечислить, что уже проверено и где именно блокер.
- Не объяснять "по памяти"; объяснять после проверки.
- Если сломался live, приоритет: стабилизировать users, затем чистить архитектуру.

## Когда задача считается завершённой

Задача закрыта только если выполнены применимые пункты:

- первопричина найдена;
- код исправлен;
- проверено не только на `admin`, но и на обычном user-контуре;
- commit запушен;
- GitHub checks зелёные;
- live обновлён и health зелёный;
- runtime подтверждает новый код;
- wiki обновлена и синхронизирована с `baza`.
