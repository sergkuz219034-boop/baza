# Workflow Codex для дебага и разработки

Канонический workflow для работы Codex с `TrafficHub`.

Цель: новый чат или новый разработчик не должен спрашивать, как подключаться, где канон и что проверять первым. Агент обязан идти по этому маршруту, пока не найден реальный блокер.

## Принципы

- Не спрашивать пользователя о подключении, каноне wiki или основном repo, пока не проверены `[[05_Эксплуатация/Доступ и подключения]]` и текущий workspace.
- Источник истины по продукту: код, runtime, БД, env, контейнеры, логи, серверные артефакты.
- Источник истины по знаниям: локальная wiki `wiki` и GitHub `sergkuz219034-boop/baza`.
- `/app` внутри контейнера не является каноническим repo. Это runtime-слой для проверки фактов.
- `/root/TrafficHub` на сервере является live host-repo для deploy, но не является wiki.
- Локальные product-клоны `TrafficHub` запрещены. Product-код читать, править, тестировать и коммитить только в server repo `/root/TrafficHub` через SSH.
- Локально держать только каноническую `wiki`, SSH-доступы и служебные скрипты подключения.
- Любой фикс считается завершённым только после проверки: локальный diff, commit, push, GitHub checks, live deploy при необходимости, runtime health, запись в wiki при наличии нового знания.
- **Иерархия моделей**: слабая модель — для простых задач (статус, список, grep), средняя — для средних (дебаг, рефакторинг, одна страница wiki), мощная — для сложных (архитектура, инцидент, многофайловые изменения, исследование).
- **Graphify** (`$graphify`) — канонический Codex skill для построения и понимания архитектуры кода. Использовать перед глубоким анализом незнакомой системы или при вопросах "как устроено", "какие связи между файлами". Для `TrafficHub` skill сначала использует локальный `graphify` CLI, а если валидный graph/scan-root недоступен, переходит на verified fallback scan по live-коду.
- Для live-поиска по коду и runtime сначала использовать `rg`; отсутствие `rg` на host или в базовых контейнерах считается defect окружения, а не нормой.

## Быстрый маршрут

1. Определить тип задачи: UI, API, worker, auth, deploy, БД, интеграция, wiki, GitHub checks.
2. Оценить риск: безопасная проверка, локальная правка UI, runtime/deploy, destructive/data-affecting.
3. Прочитать релевантные страницы wiki до правки кода.
4. Проверить код и runtime-факты, не доверять старым заметкам без подтверждения.
5. Воспроизвести симптом на минимальном контуре: `admin` и `artem`, если пользователь не указал других.
6. Исправить первопричину, а не симптом в UI.
7. Проверить, что фикс действует для всех users/owners, а не только для `admin`.
8. Запушить в GitHub и дождаться успешных checks.
9. Деплоить live только из `/root/TrafficHub`, подтянутого с `origin/main`.
10. Проверить live health и наличие нужного кода внутри контейнера `/app`.
11. Выполнить post-deploy smoke по затронутым ролям и owners.
12. Обновить wiki и синхронизировать `baza`.

## Риск-классификация перед работой

Перед любым изменением явно определить класс риска.

- `read-only`: чтение кода, логов, БД, контейнеров, GitHub checks. Техработы не нужны.
- `low-risk`: UI/CSS/текст/документация без изменения данных и фоновых задач. Техработы обычно не нужны, но нужен smoke после deploy.
- `runtime-risk`: backend, auth, scheduler, worker, очереди, Google Sheets, Rabota.ru, offer automation. Перед live-проверками включать техработы, если действие может задеть пользователей.
- `data-risk`: миграции, массовое обновление БД, очистка runtime, удаление файлов, изменение owner-scoped settings. Сначала backup/read-only план, затем точечное выполнение, затем проверка rollback path.

Если риск неочевиден, считать его `runtime-risk`, пока проверка не докажет обратное.

## Обязательный порядок при live/runtime задаче

1. Прочитать `[[05_Эксплуатация/Доступ и подключения]]`.
2. Подключаться только через SSH alias `traffichub-live`.
3. Для сложных live-команд использовать PowerShell-safe wrapper `scripts/ssh_live_bash.ps1`.
4. На сервере первым делом выполнить:
   - `whoami`
   - `cd /root/TrafficHub`
   - `git remote -v`
   - `git status -sb`
   - `git rev-parse --short=9 HEAD`
   - `command -v rg`
5. Проверить, что `/root/TrafficHub` синхронизирован с `origin/main`.
6. Пересобрать и перезапустить нужный сервис через `docker compose`.
7. Проверить `docker compose ps`, `/api/health` или публичный health endpoint.
8. Проверить, что нужные строки/файлы есть внутри контейнера `/app`, если фикс frontend/backend должен попасть в image.
9. Если задача затрагивает tooling или поиск по коду, дополнительно проверить `rg --version` на host и в релевантном контейнере.

## Обязательный порядок при баге

1. Зафиксировать симптом: кто, где, что нажал, какой лог, какой screenshot.
2. Найти похожее в:
   - `[[06_Отладка/Каталог ошибок]]`
   - `[[06_Отладка/Воркараунды]]`
   - `[[06_Отладка/Активные баги/README]]`
   - `[[06_Отладка/Решённые баги/README]]`
3. Определить зону:
   - frontend state
   - backend API
   - auth/session
   - owner/user isolation
   - Google Sheets
   - Rabota.ru API
   - offer form automation
   - worker/scheduler
   - deploy/container drift
4. Проверить факты в коде и runtime.
5. Написать минимальный фикс.
6. Проверить регрессионные инварианты.
7. Если баг повторяемый или нетривиальный, создать/обновить заметку в `06_Отладка`.

## Post-deploy smoke

После deploy проверять не только `health`, но и поведение затронутого контура.

Минимум:

- `curl -fsS https://traffic-hub.pro/api/health`;
- `docker compose ps` по затронутым сервисам;
- проверить, что нужный файл/строка есть внутри контейнера `/app`;
- проверить GitHub checks по последнему commit;
- если изменён frontend, проверить отдаваемый asset с cache-busting query;
- если изменён auth/settings/owner isolation, проверить минимум `admin` и один обычный user;
- если изменён Autolead, проверить, что логика находится в общем кодовом пути, а не в user-specific workaround;
- если менялся scheduler, проверить default-state новых users и owner-scoped расписание существующих users.

Smoke считается недостаточным, если проверен только `admin` или только наличие HTTP 200.

## Rollback path

Для live-изменений заранее понимать, как откатиться.

- Кодовый rollback: новый commit с revert/fix, push, GitHub checks, rebuild/recreate контейнера.
- Config rollback: вернуть previous value через API/БД/config, затем проверить runtime reload.
- Data rollback: использовать backup/export или точечный SQL только после read-only проверки affected rows.
- UI rollback: не чистить симптомы в браузере, пока не подтверждён фактический asset в `/app` и публичной отдаче.

`git reset --hard`, ручное редактирование `/app` и правки внутри mutable container layer не являются нормальным rollback.

## Инварианты, которые проверять почти всегда

- `admin` не должен быть единственным рабочим пользователем.
- Настройки Google Sheets, Rabota.ru API, offers, service account и runtime profile должны быть owner-scoped.
- Пользователь не должен видеть или использовать чужие настройки.
- Новые пользователи не должны наследовать мусорные admin defaults.
- Уже обработанные лиды не должны повторно отрабатываться.
- Ошибки формы оффера не должны ломать весь цикл.
- Account Manager доступен только admin.
- Maintenance mode виден users, но не должен блокировать admins.
- Live container `/app` должен соответствовать `origin/main`, а не старому mutable слою.
- GitHub checks должны быть зелёными после push.
- Любой tenant-scoped write в `traffic_hub` обязан явно передавать `tenant_id` и, где есть owner model, `owner_username`.
- Если баг виден у `artem`, `alex` или другого user, считать его общесистемным, пока код/runtime не доказал обратное.
- Если full suite green, но live logs показывают DB constraint error, доверять live DB/runtime и добавлять недостающий regression test.

## Стандарт фикса

Перед commit:

- `git status -sb`
- `git diff --check`
- релевантный тест или runtime probe

После push:

- проверить GitHub Actions;
- если checks красные, изучить логи, исправить причину и пушить новый commit;
- не говорить пользователю "готово", пока push/checks не подтверждены или блокер не описан конкретно.

При deploy:

- обновлять server repo из `origin/main`;
- не считать контейнер `/app` repo-источником;
- не создавать локальный clone/fetch checkout product repo для обхода SSH;
- после deploy проверять health;
- если SSH оборвался во время build, перепроверить контейнер отдельной командой.

## Стандарт wiki

Если в ходе работы найдено новое знание:

1. Обновить точную страницу, а не писать дубликаты.
2. Для расследования использовать структуру:
   - Симптом
   - Зона системы
   - Гипотеза
   - Проверка
   - Наблюдение
   - Вывод
   - Следующий шаг
3. Помечать гипотезы как гипотезы.
4. Ссылаться на конкретный файл, endpoint, таблицу, env, контейнер или commit.
5. В конце синхронизировать локальную wiki с `sergkuz219034-boop/baza`.

## Как отвечать пользователю

- Коротко сообщать текущий шаг и факт, который проверяется.
- Не задавать вопросы, если можно проверить самому.
- Если нужен вопрос, сначала перечислить, что уже проверено и где именно блокер.
- Не объяснять "по памяти"; объяснять после проверки.
- Если сломался live, приоритет: стабилизировать users, затем чистить архитектуру.

## Когда задача считается завершённой

Задача закрыта только если выполнены применимые пункты:

- первопричина найдена;
- код исправлен;
- проверено не только на `admin`, но и на обычном user-контуре;
- commit запушен;
- GitHub checks зелёные;
- live обновлён и health зелёный;
- runtime подтверждает новый код;
- wiki обновлена и синхронизирована с `baza`.

## Что не подходит нашему процессу

- Большие абстрактные аудиты без tied-to-runtime findings.
- Фиксы "по скрину" без проверки кода/runtime, если проблема может быть системной.
- Локальные product-клоны как способ обойти SSH или GitHub auth.
- Деплой без проверки user-contour.
- Исправления в `/app` вместо `/root/TrafficHub`.
- Закрытие задачи без записи в wiki, если найден новый повторяемый баг или архитектурный факт.
