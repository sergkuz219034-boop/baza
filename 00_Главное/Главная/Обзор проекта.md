# Обзор проекта

## Назначение

`TrafficHub` — серверный продукт с owner-scoped runtime, очередями, dashboard/API-слоем и отдельными worker/container контурами.

Главная практическая задача этой wiki: быстро привести инженера или ИИ-агента к корректной точке входа в код, runtime и инфраструктуру без полного чтения репозитория.

## Подтверждено

- live mutable repo приложения: `/root/TrafficHub`;
- внешний knowledge-layer и dev/debug wiki: этот vault;
- source of truth по поведению системы:
  - код
  - runtime
  - контейнеры
  - env/config
  - БД
  - логи

## Что важно понять за 5 минут

- это не “один FastAPI сервис”, а смешанный web + worker + runtime contour;
- owner-scope влияет на jobs, runtime state, UI-логи и отладку;
- часть старой логики живёт в legacy-слоях `services/*`, `modules/*`, `utils/*`;
- wiki не заменяет код: она должна подводить к проверяемым файлам, контейнерам и runtime-фактам.

## Storage reality check

- текущая матрица backend'ов и роль SQLite собрана в [[00_Главное/Главная/Дашборд|Дашборд]];
- здесь достаточно помнить одно: live backend reality уже PostgreSQL-first, а SQLite больше не является shorthand-объяснением системы.

## Ключевые точки входа

- web/auth/dashboard/ws: `api/server.py`
- embedded app/runtime API: `traffic_hub/app.py`
- worker execution: `traffic_hub/worker.py`
- live host contour: `150.241.70.31`
- live repo: `/root/TrafficHub`

## Ограничения канона

- если утверждение не подтверждается кодом или runtime, оно не считается фактом;
- archive-слои использовать как индекс знаний, но не как окончательный source of truth;
- при расхождении между wiki и live системой править надо канон, а не объяснять расхождение “историей”.
