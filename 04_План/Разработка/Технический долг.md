## SQLite cleanup backlog

### P1. Active runtime contract

- `utils/database.py`: держит PostgreSQL-first routing, но всё ещё содержит SQLite fallback ветки почти по всем runtime операциям;
- `utils/runtime_store_schema.py`: создаёт и мигрирует SQLite runtime-таблицы даже при PostgreSQL-first прод-контуре;
- `utils/runtime_store_maintenance.py`: остаётся SQLite cleanup path рядом с PostgreSQL-aware `utils/runtime_store_pg_maintenance.py`.

Риск:
- кодовая база продолжает выглядеть как будто production runtime может одинаково жить в двух storage-path;
- это усложняет дебаг и повышает цену изменений.

Уточнение:
- strongest confusing factor сейчас не просто fallback-ветки, а безусловный вызов `utils/runtime_store_schema.py` из `utils/database.py:init_db()`;
- детальный keep/remove boundary: [[04_План/Материалы/сырьё/документы/TrafficHub-obsidian/01 Расследования/2026-06-17 P1 boundary active runtime fallback]]

### P2. Hybrid read/metrics path

- `utils/runtime_repository.py`: owner leads/history/summary уже умеет PostgreSQL, но сохраняет SQLite branch;
- `services/stats_service.py`: postback-метрики читаются из SQLite path только если `traffic_hub` DB URL указывает на SQLite.

Риск:
- read-model и dashboard analytics труднее интерпретировать при расследованиях;
- легко перепутать fallback для локального/dev сценария с production contract.

Уточнение:
- это уже не active runtime write-path, а hybrid read/metrics stream;
- `services/stats_service.py` отдельно тащит SQLite-only логику для `postback_logs` и `conversions`;
- детальный boundary: [[04_План/Материалы/сырьё/документы/TrafficHub-obsidian/01 Расследования/2026-06-17 P2 boundary hybrid read and metrics]]
- live-проверка показывает, что `traffic_hub` product DB уже PostgreSQL-first, а значит SQLite branch в `stats_service.py` сейчас больше похож на documented metrics gap, чем на активный production path:
  [[04_План/Материалы/сырьё/документы/TrafficHub-obsidian/01 Расследования/2026-06-17 Live product DB backend for stats_service]]

### P3. Separate legacy contour

- `utils/control_store.py`: отдельный hybrid control contour с `control.db` и `CONTROL_PG_LEGACY_IMPORT`;
- это не долг active Autolead runtime migration, а отдельный migration/cleanup stream.

Риск:
- при неаккуратном cleanup можно разрушить import/compatibility path control-слоя.

Уточнение:
- live-проверка уже показывает `backend=postgres`, `legacy_import_enabled=false`, `legacy_sqlite_exists=true`;
- значит, `P3` сейчас описывается не как "control всё ещё на SQLite", а как PostgreSQL-first contour с legacy artefact trail;
- расследование: [[04_План/Материалы/сырьё/документы/TrafficHub-obsidian/01 Расследования/2026-06-17 Live control_store backend]]

### P4. Test-only surface

- `tests/test_database.py`
- `tests/test_leads_router.py`
- `tests/test_traffic_hub_migrations.py`
- другие `sqlite+aiosqlite` fixture tests для `traffic_hub`

Риск:
- низкий для production, но высокий для misleading mental model, если их читать как отражение live storage contract.

Уточнение:
- это в первую очередь fixture/integration convenience layer;
- cleanup здесь должен быть последним и отдельно от production storage streams;
- расследование: [[04_План/Материалы/сырьё/документы/TrafficHub-obsidian/01 Расследования/2026-06-17 Test-only SQLite surface]]

## Что можно рассматривать как кандидатов на следующий cleanup

1. Явно отделить в коде runtime PostgreSQL contract от SQLite fallback contract.
2. Сузить `utils/runtime_store_schema.py` до legacy/bootstrap роли или убрать из production init-path.
3. Зафиксировать, нужен ли `services/stats_service.py` SQLite branch в текущем прод-контуре.
4. Не трогать `utils/control_store.py` в одном пакете изменений с runtime cleanup без отдельного расследования.
