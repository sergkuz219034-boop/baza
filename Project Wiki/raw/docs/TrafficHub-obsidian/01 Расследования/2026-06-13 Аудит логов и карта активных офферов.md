# 2026-06-13 Аудит логов и карта активных офферов

## Симптом

- Требовалось проверить:
  - что live-логи не засорены техническим шумом;
  - что в UI виден realtime-ход задачи;
  - какие активные офферы вообще существуют в live runtime и какие из них уже выглядят рискованными по конфигу/runtime.

## Зона системы

- Live code:
  - `/root/TrafficHub/api/server.py`
  - `/root/TrafficHub/api/ws_manager.py`
  - `/root/TrafficHub/utils/runtime_logging.py`
  - `/root/TrafficHub/dashboard/app.js`

- Live runtime config:
  - `utils.license.list_license_accounts(active_only=True)`
  - `utils.control_store.load_user_config(<login>)`

## Гипотеза

- Основной шум должен отсеиваться в двух местах:
  - backend-filter (`utils.runtime_logging.py` / `api/server.py`);
  - frontend-render (`dashboard/app.js`) через special handling для `spinner`-строк.
- Даже если `/api/logs` хранит несколько heartbeat-сообщений, UI может показывать их как одну “живую” строку.

## Проверка

- По live-коду подтверждено:
  - `api/server.py` держит `_LOG_NOISE_RE` и фильтрует типовой backend-мусор;
  - `utils.runtime_logging.py` дополнительно режет low-value строки через `_UI_DROP_REGEXES` и `_UI_KEEP_SUBSTRINGS`;
  - `api/ws_manager.py` публикует owner-scoped log payload и не смешивает пользователей;
  - `dashboard/app.js` обрабатывает `spinner=true` особым образом:
    - ищет существующую `.log-spinner`;
    - перерисовывает её вместо накопления новых строк;
    - не плодит ленту heartbeat-дублями в UI.

## Наблюдение

- Логическая модель логов сейчас корректная:
  - backend и frontend оба режут шум;
  - realtime heartbeat в UI должен схлопываться до одной живой строки;
  - owner-scoped изоляция есть и по websocket, и по `/api/logs`.
- Шум в live-логе сейчас ограничен архитектурно и дополнительно уменьшен в sender-runtime:
  - multi-line `Page.goto ... Call log ...` больше не должен попадать в пользовательскую ленту целиком;
  - вместо этого sender пишет короткий `Ошибка <оффер>: ...`.
- Ранний грубый smoke с простым поиском полей по первому DOM дал ложные отрицания для части `leadsu/tilda` офферов.
- Более надёжным оказался smoke по фактическому redirect chain и конечному DOM домена назначения.
- По active offers есть чёткое разделение:
  - runtime живые/открываемые:
    - `alex / Ozon`
    - `admin / Онекта`
    - `alex / Онекта`
    - `alex / Воксис`
    - `ARTEM2 / Воксис`
    - `Artem / Воксис`
    - `Artem / Онекта`
    - `ARTEM2 / X5`
    - `ARTEM2 / Дикси`
    - `ARTEM2 / ВкусВилл`
  - живые, но нестабильные по upstream redirect:
    - `ARTEM2 / Самокат`
  - upstream-risks / external blockers:
    - `ARTEM2 / Я еда` → partner disabled
    - `ARTEM2 / Четыре лапы` → partner disabled
- Отдельная причина `2026-06-14`:
  - у `Artem` и `ARTEM2` был битый `rabota_ru.proxy_url`, из-за чего часть офферов раньше ложно выглядела как мёртвая.
  - после code hardening этот конкретный класс ошибки не должен возвращаться через штатный settings flow.
  - дополнительно найден отдельный runtime-баг retry-ветки:
    - `process_retry_queue()` мог повторно отбрасывать уже выбранный retry-оффер как `нет оффера`
    - причина была не в лендинге, а в повторном vacancy-matching внутри `run_sender()`
    - после server-side fix retry-лид `artem / Воксис` дошёл до реальной платформенной попытки и завершился как `duplicate`, а не как ложный `SKIP`

## Вывод

- По логам:
  - подтверждённый кодом вывод: UI-лента должна быть компактной и realtime;
  - подтверждённый runtime-ответ `/api/logs`: пользователь получает одну короткую строку ошибки без raw `Call log`;
  - текущая архитектура логов не выглядит шумной по design intent;
  - heartbeat-дубли специально схлопываются на фронте;
  - sender-runtime теперь не должен вываливать в UI сырые Playwright `Call log`.
- По офферам:
  - активный live парк проверен фактическим smoke по текущим профилям;
  - `alex/Ozon`, `ARTEM2/X5`, `Artem/Воксис` после proxy-fix и rebuild стали стабильными;
  - часть проблем сидит не в DOM-селекторах, а в самих redirect-маршрутах:
    - `ARTEM2`: upstream-disabled `Я еда`, `Четыре лапы`;
    - `ARTEM2 / Самокат`: нестабильный redirect/timeout.

## Следующий шаг

- Если нужен полный operational green-state по всем офферам:
  - отдельно разбирать `ARTEM2 / Самокат` как flaky route
  - не тратить время на `Я еда` и `Четыре лапы`, пока upstream отдаёт `disabled.html`
  - для `ВкусВилл` проверять именно `VkusvillLeadsuPlatform`, если нужен не route-smoke, а строгий submit-smoke
