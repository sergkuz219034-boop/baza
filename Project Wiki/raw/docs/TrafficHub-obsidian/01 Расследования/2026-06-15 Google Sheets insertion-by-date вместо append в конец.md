# 2026-06-15 Google Sheets insertion-by-date вместо append в конец

## Симптом

- пользователь зафиксировал требование:
  - новые строки должны вставляться в правильное место по `Дата`, а не просто добавляться в конец таблицы;
  - если дата уже существует, строки должны вставляться в конец блока этой даты;
  - если даты ещё нет, строки должны вставляться между соседними датами;
  - внутри одной даты порядок должен сохраняться по порядку выгрузки.

## Зона системы

- `modules/sheets_sync.py`
- `upload_to_sheets()`
- `append_processed_leads()`

## Гипотеза

- текущий runtime всё ещё опирается на `append_rows()` с последующей полной сортировкой листа по `Дата`;
- это логически выполняет порядок по дате, но слишком грубо для пользовательского требования и хуже с точки зрения формул/форматирования.

## Проверка

- подтверждено в `modules/sheets_sync.py` до правки:
  - `upload_to_sheets()` добавлял новые строки батчами через `worksheet.append_rows(batch, ...)`;
  - `append_processed_leads()` тоже делал `append_rows(rows, ...)`, после чего вызывал `_sort_worksheet_by_date(...)`;
- это означало:
  - место вставки выбиралось не по дате, а фактически как конец листа;
  - правильный порядок достигался постфактум через полную перепись диапазона.
- добавлены unit-тесты в `tests/test_sheets_queues.py`:
  - вставка новой даты между существующими блоками;
  - вставка в конец уже существующего блока даты;
  - сохранение порядка строк внутри одной даты.
- regression-smoke подтверждён в runtime-container:
  - `tests/test_sheets_queues.py`
  - `tests/test_leads_service_sheets_flow.py`
  - итог: `10 passed`.
- дополнительно выполнен live smoke на реальном Google Sheets worksheet:
  - использована временная вкладка `ZZ_debug_insert_*` внутри существующей доступной таблицы;
  - после двух волн вставки runtime вернул:
    - `["A", "01.06.2026"]`
    - `["C", "02.06.2026"]`
    - `["B", "03.06.2026"]`
    - `["D", "03.06.2026"]`
  - это подтверждает:
    - дата `02.06.2026` была вставлена между соседними датами;
    - новая строка `03.06.2026` встала в конец уже существующего блока `03.06.2026`.
- попытка создать отдельные временные spreadsheet-файлы для smoke упёрлась в внешний runtime-блокер:
  - `APIError: [403]: The user's Drive storage quota has been exceeded`
  - поэтому для live-проверки использована временная вкладка в уже существующей таблице с последующим удалением.

## Наблюдение

- в `modules/sheets_sync.py` введён helper insertion-path:
  - `_group_rows_by_date(...)`
  - `_find_insert_row_by_date(...)`
  - `_insert_rows_chronologically(...)`
- новый path использует `worksheet.insert_rows(...)`, а не только `append_rows(...)`;
- для mixed-date батча runtime:
  - сначала стабильно группирует строки по дате;
  - затем ищет позицию вставки для каждой даты;
  - вставляет строки сразу в правильный блок листа.

## Вывод

- каноническое поведение теперь соответствует user requirement точнее, чем старая схема `append + full sort`:
- `pending` и `processed` остаются отсортированными по `Дата`;
- новые строки встраиваются сразу в нужное место;
- внутри одной даты сохраняется порядок текущей выгрузки/обработки;
- runtime меньше переписывает весь лист целиком.
- strongest current evidence:
  - unit-tests на fake worksheet;
  - regression-smoke service flow;
  - live insertion smoke на реальном worksheet Google Sheets.
