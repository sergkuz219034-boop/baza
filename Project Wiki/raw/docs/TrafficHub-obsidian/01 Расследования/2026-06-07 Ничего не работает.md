# 2026-06-07 Ничего не работает

## Симптом

- Пользователь сообщает: `до сих пор ничего не работает`.
- Предыдущие частичные фиксы по `jobs`, `user settings`, `Playwright interrupt` были задеплоены, но пользователь не подтверждает восстановление сценария в браузере.

## Зона системы

- Web dashboard: `dashboard/index.html`, `dashboard/app.js`
- Jobs API: `api/routers/jobs.py`
- Очередь и state: `traffic_hub/services/job_queue.py`, `utils/state.py`
- Worker: `traffic_hub/worker.py`, `traffic_hub/services/job_runner.py`
- Конфигурация user-профиля: `api/routers/settings.py`, `services/leads_service.py`
- Runtime-контур: Docker Compose, Redis, PostgreSQL, `autolead_server_bot`, `traffichub_worker`

## Гипотеза

1. Базовая серверная инфраструктура уже жива, а поломка проявляется на конкретном пользовательском сценарии или профиле.
2. Часть старой документации вводит в заблуждение и мешает локализации, потому что описывает устаревшую SQLite/one-process архитектуру.
3. Возможен remaining bug на живом UI, который не воспроизводится простым API-smoke.

## Проверка

- Проверен runtime health:
  - `https://traffic-hubcrm.ru/api/health` -> `{"status":"ok","control":{"backend":"postgres"}}`
- Проверены контейнеры по `docker-compose.yml` и runtime:
  - `autolead_server_bot`
  - `traffichub_worker`
  - `traffichub_postgres`
  - `traffichub_redis`
  - `traffichub_license_auth`
  - `traffichub_license_server`
  - `traffichub_account_manager`
  - `traffichub_caddy`
- Проверена очередь:
  - `traffic_hub:jobs:queue` length = `0`
  - active set пустой
- Проверены known job state:
  - `traffic_hub:jobs:state:admin` -> `idle`
  - `traffic_hub:jobs:state:alex` -> `idle`
- Прямой smoke внутри контейнера:
  - `user` может сохранять `google_sheets_pending_spreadsheet_id` и `google_sheets_processed_spreadsheet_id`
  - `user` не может переписывать `access_admin_users`
  - повторный `POST /api/jobs/run` для того же пользователя возвращает `202 already_running`
- Проверены свежие логи за 2 часа:
  - новых `ERROR`, `Traceback`, `Cannot switch to a different thread` не найдено

## Наблюдение

- Серверная платформа в целом жива.
- Исправления по backend применены и запушены, но это не доказывает, что реальный пользовательский сценарий в браузере восстановлен.
- Smoke не покрывает:
  - реальные credentials пользователя;
  - фактические Google Sheets ID;
  - реальные Rabota/Playwright данные;
  - поведение браузерного frontend на конкретной странице после кэша/старой сессии.
- Legacy wiki устарела и противоречит runtime:
  - локальный `[[01-Architecture/Overview]]` описывает one-process + SQLite;
  - server wiki `wiki/concepts/architecture.md` всё ещё описывает встроенную `/traffic/` SPA как действующую модель.
- Дополнительная runtime-проверка 2026-06-08 показала конкретную картину по `admin`:
  - `run` реально стартует и завершается в worker, это подтверждено логами `traffic_hub/services/job_runner.py`.
  - Проблема `ничего не начинается` была частично ложным симптомом: цикл работал, но значительная часть лидов уходила в `SKIP`, поэтому с точки зрения пользователя не было видимого результата.
  - Источник красного спама в логах был отдельным дефектом: `modules/rabota_api.py:get_messages()` вызывал legacy endpoint `POST /v4/me/company/chats.json`, который на проде стабильно отвечает `404`.
  - Для `admin` effective runtime config в момент починки содержал один активный оффер `Онекта` с `vacancy_ids=[54257329]`.
  - По live leads queue для `admin`:
    - `load_leads_for_send(days=3650)` -> `596` лидов;
    - из них `416` матчились к `offer_mapping`;
    - во время smoke-run worker реально выполнил отправку: `sent=10`, `errors=0`.
  - Шум `нет оффера для vacancy_id` тоже оказался отдельной проблемой наблюдаемости: лог печатал по строке на каждый неподходящий лид.

## Вывод

- На уровне инфраструктуры и API нет явной общей аварии.
- Текущая формулировка `ничего не работает` недостаточна как доказательство общей серверной поломки.
- Следующий уровень расследования должен идти от конкретного пользовательского сценария:
  - какой логин;
  - какая кнопка;
  - какой HTTP-ответ;
  - меняется ли job state;
  - что пишет `autolead.log` в момент клика;
  - есть ли валидные user-specific settings и external creds.
- Подтверждённые первопричины по состоянию на 2026-06-08:
  1. Входящие сообщения Rabota.ru были привязаны к удалённому endpoint и создавали ложный аварийный фон в UI/logs.
  2. Пользовательские профили ранее могли загружаться из пустой/disabled-базы настроек, что отключало `responses/autofit/google_sheets`.
  3. Реальный результат `run` для `admin` зависел от effective `offer_mapping`, а не от самой очереди задач.

## Следующий шаг

1. Проверить через браузер `admin`, что UI после перезапуска показывает обновлённый лог без `404 chats.json`.
2. Прогнать тот же сценарий на остальных пользователях и подтвердить:
   - owner-scoped config;
   - owner-scoped Sheets queue;
   - owner-scoped run status.
3. Отдельно расследовать, почему effective `offer_mapping` у `admin` отличается от ожидаемого полного набора офферов и сводится к одному офферу `Онекта`.
4. После верификации обновить:
   - [[03 Плейбуки/Jobs и Worker]]
   - [[04 Сущности/Job Queue]]
   - [[04 Сущности/Control Store]]

## Дополнение 2026-06-08: удаление пользователей из admin панели

### Симптом

- Кнопка удаления пользователя в admin панели не удаляет профиль.
- Пользователь просит оставить только профили, у которых есть Rabota API credentials.

### Зона системы

- Admin UI: `dashboard/app.js`
- License API: `api/routers/settings.py`
- Runtime user store: `utils/license.py`, `utils/control_store.py`
- PostgreSQL tables: `users`, `control_license_users`, `control_user_app_auth`, `tenant_memberships`, `funnels`

### Гипотеза

1. UI вызывает корректный endpoint, но PostgreSQL delete ломается на внешних ключах.
2. Admin панель показывает список не из `control_license_users`, а из runtime-таблицы `users`, поэтому частичное удаление выглядит как "ничего не произошло".

### Проверка

- Проверен runtime-path удаления:
  - frontend `deleteLicenseAccount(login)` -> `DELETE /api/license-accounts/{login}`
  - backend -> `utils/license.py::delete_license_user()`
- Подтверждено, что в PostgreSQL-режиме удаление шло не через полную очистку runtime, а через неполный path.
- После первой правки удаление всё ещё падало по FK:
  - `tenant_memberships_user_id_fkey`
  - затем `funnels_created_by_fkey`
- Проверен список runtime-пользователей через `utils.license.list_license_accounts(active_only=False)` и join `users` + `control_user_app_auth`.

### Наблюдение

- Источник истины для списка admin панели в PostgreSQL-режиме: таблица `users`, а не только `control_license_users`.
- Удаление пользователя в таком режиме обязано чистить минимум:
  - `control_license_users`
  - `control_user_app_configs`
  - `control_user_app_auth`
  - `tenant_memberships`
  - `funnels`
  - `users`
- На момент расследования лишними без Rabota API были `audit-user-a` и `audit-user-b`.
- После расширения delete path и rebuild `autolead_server_bot` эти пользователи были удалены успешно.
- Финальный runtime-список пользователей с Rabota API:
  - `admin`
  - `alex`
  - `Artem`
  - `Artemka`
  - `legacy_859`
  - `legacy_probe`

### Вывод

- Поломка кнопки delete была серверной, а не фронтовой.
- Первопричина: неполный каскад удаления в PostgreSQL runtime и расхождение между `control_license_users` и `users`.
- Критерий "оставить только пользователей с Rabota API" нужно проверять по `control_user_app_auth`, а не по старым sheet/runtime-спискам.

### Следующий шаг

1. Если `legacy_859` и `legacy_probe` больше не нужны бизнесу, удалить их отдельно уже как валидные runtime-профили с credentials.
2. Отдельно задокументировать ownership runtime-пользователей и зависимость admin панели от таблицы `users`.

## Дополнение 2026-06-09: `Резюме`-вкладка и `PermissionError()` в Sheets

### Симптом

- Пользователь попросил добавить вкладку `Резюме` в основную Google Sheet и собирать резюме каждого кандидата.
- На скриншотах и в старых логах был виден `PermissionError()` в фазе Google Sheets:
  - `Sheets upload error: PermissionError()`
  - `Ошибка чтения отработанной таблицы: PermissionError()`
  - `Ошибка загрузки неотработанных лидов: PermissionError()`

### Зона системы

- `services/leads_service.py`
- `modules/sheets_sync.py`
- `api/routers/settings.py`
- runtime secrets:
  - `/app/data/runtime/secrets/config.json`
  - `/app/data/runtime/secrets/service_account.json`
  - `/app/data/runtime/secrets/service_account__alex.json`

### Гипотеза

1. Ошибка связана с ACL Google Sheets или неправильным service account.
2. Ошибка может быть следствием старого image/container, который не подхватил новые фиксы.
3. Нужен отдельный экспорт raw-резюме, но он не должен ломать основной поток лидов.

### Проверка

- В runtime контейнере подтверждено:
  - `service_account.json` и `service_account__alex.json` оба могут `open_by_key()` все три workbook ID:
    - `10tCmh8ZFbHhmNohrZRNedfY81K2_olYJnjk623HRnMY`
    - `1seCE2MPKZV01LJMvL4CuvSDL7IdG-V_vN6hmqoAcZOs`
    - `1vu2zNVWqMAl_jU3gs8AgCeDTxIFhvXHt1U5tHLID4m8`
  - оба service account могут `append_row()` в pending/processed/main sheets.
  - `load_pending_leads_for_send(config)` в текущем контейнере возвращает данные и не падает.
  - `get_processed_contact_keys(config)` в текущем контейнере тоже работает.
- Проверен compose/runtime:
  - код не был смонтирован в контейнер как bind mount;
  - изменения на хосте нужно было собирать в image;
  - `autolead_bot` и `worker` пересобраны и перезапущены.
- В код добавлен новый export:
  - `upload_resumes_to_sheets(...)`
  - raw-резюме собираются в `run_scraper()` и выгружаются в лист `Резюме`.

### Наблюдение

- Для `alex` существует owner-scoped `google_sheets.service_account_file = /app/data/runtime/secrets/service_account__alex.json`.
- Старые runtime логи могли быть сняты до пересборки image; после rebuild контейнеров часть ошибок не воспроизводилась в прямых smoke-вызовах.
- Поздняя проверка 2026-06-09 подтвердила отдельный класс проблемы:
  - role-specific `pending_spreadsheet_id` / `processed_spreadsheet_id` могут быть недоступны текущему service account;
  - `gspread.open_by_key(...)` в этом случае даёт `PermissionError`;
  - это ломает `upload_to_sheets()`, `get_processed_contact_keys()` и `load_pending_leads_for_send()`, но код не должен подменять role workbook основной таблицей.
- Экспорт `Резюме` теперь идёт как отдельный лист в workbook и не должен блокировать основной `upload_to_sheets()`.

### Вывод

- `PermissionError()` имеет два подтверждённых источника риска:
  - live контейнеры могут работать на старом image после правки файлов на хосте;
  - пользовательский профиль может хранить недоступные role-specific Sheet ID.
- Для второго случая принято правило fail-closed:
  - если `pending` или `processed` workbook недоступен или не задан;
  - код не использует основной `google_sheets.spreadsheet_id`;
  - ошибка фиксируется в логах как проблема доступа/конфигурации конкретного role workbook;
  - исправление делается через выдачу service account доступа к нужной таблице или замену role-specific ID.
- Для `Резюме` добавлено ограничение длины ячейки, чтобы Google Sheets не падал на лимите `50000 characters in a single cell`.

### Следующий шаг

1. При новых Sheets-ошибках сначала проверять:
   - `google_sheets.service_account_file`;
   - доступность `spreadsheet_id`;
   - доступность `pending_spreadsheet_id` и `processed_spreadsheet_id`;
   - лог `fallback на основной workbook запрещен`, если role workbook недоступен.
2. Если ошибка повторится, снимать уже не summary-log, а точный traceback из контейнера.
3. Следить, чтобы после правки файлов на хосте всегда выполнялся rebuild `autolead_bot` и `worker`.
