# Развёртывание

## Подтверждённый deployment contour

- docker-compose product stack
- caddy как внешний reverse proxy/public entry
- отдельные контейнеры worker, account_manager, postgres, redis, license services

## Что важно

- live поведение проверять по контейнерам и health endpoints;
- изменение deployment без сверки runtime и логов недопустимо.
- backend reality проверять не по наличию `autolead.db`/`control.db` на volume, а по live env, container health и runtime status функций.
- live доступ начинать только через canonical SSH contour `[[05_Эксплуатация/Доступ и подключения]]`.
- режим техработ проверять и менять через backend/container runtime (`/api/settings/maintenance-mode` или `docker exec autolead_server_bot ... load_config/save_config`), а не только через host-side `python3` из `/root/TrafficHub`; см. [[01_Расследования/2026-06-23 Maintenance mode host-container config drift]].
- production-readiness check перед выпуском: `git status`, GitHub checks, `docker compose ps`, `/api/health`, `pytest -q`, read-only DB smoke по tenant constraints и проверка последних `docker logs` на `IntegrityError`.

# Канон live-развёртывания

- Серверный git checkout: `/root/TrafficHub`.
- Сборка контейнеров выполняется только из `/root/TrafficHub/docker-compose.yml`.
- Контейнерный `/app` не является каноническим репозиторием: это build artifact и mutable runtime-layer.
- Постоянные данные и secrets остаются на host:
  - `/root/TrafficHub/data/runtime`
  - `/root/TrafficHub/data/logs`
  - `/root/TrafficHub/data/debug`
  - `/root/TrafficHub/data/backups`
  - `/root/TrafficHub/secrets`

# Правило деплоя

- Правки вносятся в `/root/TrafficHub`.
- Затем выполняются `docker compose build ...` и `docker compose up -d --force-recreate ...` из `/root/TrafficHub`.
- Hotfix напрямую в `/app` допустим только как аварийная временная мера; после этого изменения обязаны быть перенесены обратно в `/root/TrafficHub`.

# Доменный контур

- Primary domain: `traffic-hub.pro`.
- Legacy/fallback domain: `traffic-hubcrm.ru`.
- Account Manager: `am.traffic-hub.pro`, fallback `am.traffic-hubcrm.ru`.
- License auth: `auth.traffic-hub.pro`, fallback `auth.traffic-hubcrm.ru`.
- Hermes доступен через основной reverse proxy path `/hermes`.

## Удалённый Hermes subdomain

- `hermes.traffic-hubcrm.ru` не является рабочим доменом и не должен присутствовать как отдельный Caddy site block.
- Причина: DNS для этого subdomain отсутствует, Caddy уходит в повторные ACME/NXDOMAIN попытки и засоряет runtime logs.
- Подтверждённый фикс: product commit `e7fc6b041 fix: remove dead hermes subdomain from caddy`.
- Проверка после фикса:
  - `rg -n 'HERMES_DOMAIN|hermes\.traffic-hubcrm\.ru' deploy/Caddyfile` не должен находить site block;
  - `docker logs --since 30m traffichub_caddy | rg -i 'hermes\.traffic-hubcrm|NXDOMAIN'` не должен показывать новые попытки после reload;
  - `https://traffic-hub.pro/api/health` и `https://traffic-hubcrm.ru/api/health` должны отвечать `status=ok`.

## Hermes на `am.*`

- `am.traffic-hub.pro` и `am.traffic-hubcrm.ru` обслуживают основной Account Manager через `account_manager:8000`.
- Hermes-related paths на этих доменах должны идти в контейнер `hermes:9119`, а не на host/dev port.
- Запрещённый production target: `172.22.0.1:3000`. Если он снова появился в `deploy/Caddyfile`, это regression.
- Быстрая проверка:
  - `rg -n '172\.22\.0\.1:3000' deploy/Caddyfile` не должен ничего находить;
  - `docker logs --since 30m traffichub_caddy | rg -i '172\.22\.0\.1:3000|connection refused|status":502'` не должен показывать новые строки после reload/recreate.
