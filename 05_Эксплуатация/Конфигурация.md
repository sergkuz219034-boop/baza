## Что проверять первым

- какой compose/env слой сейчас реально поднят;
- совпадает ли `DATABASE_URL` с ожидаемым PostgreSQL-first контуром;
- не маскируется ли runtime legacy-fallback артефактами;
- совпадает ли текущий worker parallelism с ожидаемым режимом исполнения.
- не осталось ли отключённым один из флагов `AUTOLEAD_RUNTIME_*_BACKEND=postgres`, из-за чего часть runtime тихо вернётся на SQLite fallback.

## Почему это важно

- многие баги выглядят как code defect, но на деле являются config drift;
- старые заметки про `control.db` и SQLite больше нельзя считать достаточным объяснением текущего поведения.
- active runtime-контур уже зависит от согласованности PostgreSQL backend flags, а не только от наличия `autolead.db`.

## Практический вывод

- если все `AUTOLEAD_RUNTIME_*_BACKEND` включены в `postgres`, `autolead.db` не должен считаться главным evidence runtime-поведения;
- если один из backend flags выключен или переопределён, поведение может стать hybrid и диагностику придётся делать по конкретной подсистеме;
- `control_store` надо диагностировать отдельно: его наличие не доказывает, что Autolead runtime всё ещё сидит на SQLite.
