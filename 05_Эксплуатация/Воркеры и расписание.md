# Воркеры и расписание

## Подтверждено

- отдельный контейнер `traffichub_worker`
- модель исполнения: subprocess-per-owner
- default live parallel owners: `2`
- heartbeat file:
  - `/app/data/runtime/worker.heartbeat`
- worker healthcheck считает контейнер healthy, если heartbeat-файл моложе `180` секунд
- live web-layer отдельно крутит hourly `partner_sync` loop в `autolead_server_bot`, а не в `traffichub_worker`

## Scheduler / loops

- background loops живут не только в worker, но и в web-layer;
- `api/server.py` создаёт `partner_sync_task` через lifespan;
- live log подтверждал hourly `partner_sync` для `audit-admin`:
  - `2026-06-17 00:27:33`
  - `2026-06-17 01:27:33`

## Что важно для дебага

- зависание одного owner-job может менять общую картину исполнения;
- проверять надо не только очереди, но и heartbeat, parallel owner limit и runtime log feed;
- scheduler и worker нельзя описывать как один фоновой цикл: это набор разных execution paths;
- если пропал `partner_sync`, смотреть сначала web-container `autolead_server_bot`, а не worker logs.

## Главные вопросы при расследовании

- job вообще был поставлен в очередь или потерялся раньше;
- worker поднят и пишет heartbeat;
- owner-context не сериализует весь контур сильнее, чем ожидалось;
- UI получает финальный runtime state, а не устаревший snapshot.
