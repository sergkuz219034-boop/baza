# Documentation synchronization audit

Теги: #решение

## Контекст

Нужно было привести документацию в состояние, при котором новый инженер или ИИ-агент может опираться на код, а не на устаревшие заметки.

## Что обнаружено

### 1. Workspace не является полным репозиторием

- Где найдено: корень workspace, `remote_files`, `remote_server_snapshot`
- Почему устарело старое восприятие: прежние заметки местами описывали систему как доступный full repo
- Как на самом деле: текущий workspace содержит частичные зеркала и partial snapshot, поэтому часть выводов можно делать только с оговоркой о неполном покрытии

### 2. Старые архитектурные страницы делают слишком сильные утверждения о полноте исходников

- Где найдено: `05 Решения/2026-06-01 architecture map current server.md`
- Почему устарело: заметка смешивает live server observations и локальный workspace как будто это одна и та же поверхность истины
- Как на самом деле: каноном для этой синхронизации является только код, который реально лежит в workspace

### 3. Инвентарь API в старых заметках шире, чем подтверждает текущий workspace

- Где найдено: `05 Решения/2026-06-01 db and api inventory current sources.md`
- Почему устарело: документ перечисляет API-группы, часть которых в текущем snapshot отсутствует или подтверждается только импортами
- Как на самом деле: в workspace полноценно подтверждены `jobs.py`, `settings.py` и часть TrafficHub routers; остальные роутеры нужно считать частично подтверждёнными

### 4. Frontend был описан косвенно, но без честной фиксации пробела в исходниках

- Где найдено: старые обзорные заметки
- Почему устарело: создаётся впечатление, что frontend-контур локально доступен для полноценного анализа
- Как на самом деле: в workspace подтверждено только наличие dashboard entrypoints и static serving у AccountManager

### 5. README для корня workspace отсутствовал

- Где найдено: корень workspace
- Почему устарело: новый инженер не получал объяснения, что именно представляет собой этот каталог
- Как на самом деле: нужен README, который сначала объясняет природу workspace, а потом уже архитектуру целевой системы

## Что обновлено

- создан `README.md`
- создан `CHANGELOG.md`
- созданы `docs/architecture.md`, `docs/api.md`, `docs/deployment.md`
- созданы канонические wiki-страницы в `02 Архитектура`
- создан playbook `03 Плейбуки/Debugging.md`
- созданы entity pages в `04 Сущности`

## Какие знания отсутствовали в документации

- честное описание границ snapshot
- разделение между runtime DB, control DB, TrafficHub DB и AccountManager DB
- единая карта auth/authz
- явное описание multi-tenant механики через `owner_username`
- различие между operational API и TrafficHub API

## Что рекомендуется поддерживать дальше

- при появлении новых snapshot сразу актуализировать `API.md` и `Frontend.md`
- документировать каждый новый auth boundary отдельно
- поддерживать список непокрытых исходников, а не маскировать пробелы предположениями
