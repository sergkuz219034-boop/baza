# Secret Rotation Priority Plan

Дата: 2026-06-01
Основано на:

- `05 Решения/2026-06-01 redacted secret inventory.md`
- `05 Решения/2026-06-01 operational map current deployment.md`
- live `.env` inspection в redacted-виде

Значения секретов в документ **не включаются**.

## Анализ

Ротацию нельзя делать как одну “большую замену всех значений”, потому что:

- один `.env` одновременно кормит несколько сервисов;
- разные классы секретов имеют разный blast radius;
- часть секретов участвует в auth boundary и может мгновенно заблокировать вход пользователей;
- часть секретов затрагивает только внешние интеграции и может ротироваться отдельно.

Поэтому безопаснее делить ротацию на волны.

## Причина

### 1. Неодинаковый blast radius разных секретов

- Описание проблемы: разные группы секретов влияют на разные контуры.
- Первопричина: единый `.env` смешивает auth, perimeter, partner credentials и provider API keys.
- Критичность: `Critical`
- Возможные последствия:
  - если ротировать всё сразу, трудно локализовать регрессию;
  - легко сломать несколько сервисов одновременно.
- Рекомендуемое исправление:
  - ротировать по волнам, начиная с наибольшего security impact.

## План исправления

### Волна 1. `Critical`

Цель:

- уменьшить риск немедленного компромисса auth/perimeter контуров.

Классы секретов:

- `SESSION_SECRET_KEY`
- связанные external auth signing / verification secrets и key material
- `LICENSE_AUTH_*`, влияющие на issuer/signing path
- `ACCOUNT_MANAGER_BASIC_AUTH_HASH`
- `AI_AGENT_BASIC_AUTH_HASH`

Сервисы:

- `autolead_bot`
- `license_auth`
- `account_manager`
- `caddy`

Почему это первая волна:

- эти значения дают прямой доступ к auth/perimeter flows;
- их утечка опаснее, чем утечка provider quota;
- они формируют security posture сразу нескольких внешних входов.

Риск регрессии:

- можно сломать login-flow;
- можно нарушить token verification;
- можно заблокировать межсервисную auth-совместимость.

Безопасная стратегия:

1. Сначала подготовить новые значения.
2. Зафиксировать, какие сервисы должны читать их синхронно.
3. Менять только в окно контролируемого обслуживания.
4. Сразу проверять:
   - логин;
   - issuance/verification токенов;
   - доступ через public domains.

### Волна 2. `High`

Цель:

- закрыть доступ к внешним бизнес-интеграциям и коммуникационным каналам.

Классы секретов:

- `LEADSU_*`
- `LOVKO_*`
- `TELEGRAM_API_ID`
- `TELEGRAM_API_HASH`
- `TELEGRAM_BOT_TOKEN`

Сервисы:

- в первую очередь `autolead_bot`
- связанный integration / automation layer

Почему это вторая волна:

- утечка опасна и бизнес-чувствительна;
- но эти секреты обычно не ломают основной вход в систему так быстро, как auth/perimeter secrets.

Риск регрессии:

- обрыв partner API calls;
- сбой Telegram automation;
- частичная деградация отдельных бизнес-процессов.

Безопасная стратегия:

1. Ротировать по одной интеграции за раз.
2. После каждой ротации проверять конкретный сценарий интеграции.
3. Не совмещать с ротацией auth secrets.

### Волна 3. `Medium`

Цель:

- сократить утечку paid-provider и AI automation surface.

Классы секретов:

- `DEEPSEEK_API_KEY`
- `FREELMAPI_API_KEY`
- `OPENROUTER_API_KEY`
- `CLOSEROUTER_API_KEY`

Сервисы:

- AI / tooling layer

Почему это третья волна:

- это важно, но обычно менее критично для базовой доступности платформы;
- blast radius чаще ограничивается quota abuse и внешними AI сценариями.

Риск регрессии:

- отказ AI-инструментов;
- ошибки automation, завязанных на LLM;
- деградация вспомогательных workflow.

Безопасная стратегия:

1. Проверять каждый provider отдельно.
2. Ротировать по одному vendor-классу.
3. Сохранять rollback plan на случай неверного нового ключа.

### Волна 4. `Low/Config hygiene`

Цель:

- убрать ложные ожидания и уменьшить noise в env surface.

Классы:

- неиспользуемые или drift-переменные;
- например `ACCOUNT_MANAGER_BASIC_AUTH_*`, если будет решено не использовать basic auth на этом контуре.

Почему это последняя волна:

- это больше про честность конфигурации и снижение путаницы;
- это важно, но не так срочно, как реальная компрометация auth/perimeter или partner credentials.

## Diff

Изменений в коде или deployment не вносилось.

Добавлен документ:

Почему это безопасно:

- plan не меняет значения и не раскрывает их;
- он помогает проводить ротацию как контролируемую операцию, а не как хаотическую замену всего `.env`.

## Риски

- Если начать с низкоприоритетных ключей, а auth/perimeter secrets оставить как есть, реальный риск останется высоким.
- Если ротировать несколько волн одновременно, будет трудно понять источник регрессии.
- Если не разделить rotation window по сервисам, можно получить каскадные ошибки.

## Проверка после исправления

Для каждой волны проверка должна быть отдельной.

### Для `Critical`

- вход пользователей работает;
- токены выпускаются и валидируются;
- доступ через публичные домены не ломается;
- basic auth/perimeter ведёт себя ожидаемо.

### Для `High`

- partner API calls проходят;
- Telegram интеграции работают;
- ключевые бизнес-сценарии не деградировали.

### Для `Medium`

- AI-провайдеры отвечают;
- инструменты и automation не падают на новых ключах.

## Дополнительные улучшения

- После первой успешной волны имеет смысл разнести env surface по сервисам:
  - отдельный auth/env
  - отдельный integrations/env
  - отдельный AI/env
  - отдельный perimeter/env
- Это уменьшит blast radius последующих ротаций и сделает incident response проще.
