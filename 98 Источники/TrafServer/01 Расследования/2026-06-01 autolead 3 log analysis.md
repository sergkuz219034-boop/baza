Источник: `C:\Users\Арт\Downloads\autolead (3).log`

## Анализ

Лог покрывает один реальный цикл `run` с `15:00:05` до `15:01:16`.

Подтверждённый ход цикла:

1. Сбор лидов:
- получено 21 отклик;
- автоподбор дал 0 новых резюме;
- в БД сохранено 16 лидов;
- итог по фазе: `Итого лидов: 21`

2. Выгрузка в Google Sheets:
- началась корректно;
- попытка открытия/записи в Google Sheets зависла;
- затем получен timeout:
  - `HTTPSConnectionPool(host='sheets.googleapis.com', port=443): Read timed out. (read timeout=45.0)`
- после этого лог пишет:
  - `В Sheets добавлено строк: 0`

3. Рассылка:
- pending queue из Sheets оказалась пустой;
- затем пошла обработка `retry_queue` (`33` записей);
- практически все записи шли по сценарию:
  - `[SKIP] ... — нет оффера для vacancy_id ...`
- в `15:01:16` обработка retry queue была прервана по `/stop`;
- обработано `28 из 33`

Итог цикла:

- `Найдено: 21`
- `Sheets: 0`
- `Отправлено: 0`
- `Ошибок: 0`

## Причина

### 1. Сбой выгрузки в Google Sheets не поднимается до уровня ошибки цикла

- Описание проблемы: фаза выгрузки в Sheets фактически проваливается, но итоговый цикл не считается ошибочным.
- Первопричина: timeout при обращении к `sheets.googleapis.com` обрабатывается как локальная ошибка выгрузки, после чего цикл продолжает работу и пишет итог без ошибок.
- Критичность: `High`
- Последствия:
  - операторы видят “Ошибок: 0”, хотя критичная фаза не выполнилась;
  - downstream-фазы работают на неполных данных;
  - появляется ложное ощущение успешного run.
- Рекомендуемое исправление:
  - повышать статус цикла при провале Sheets upload;
  - отличать `partial success` от полностью успешного run;
  - логировать это как фазовую ошибку верхнего уровня.

### 2. Retry queue вырождается в массовые SKIP из-за отсутствующих офферов

- Описание проблемы: retry queue активно крутится, но элементы не отправляются, потому что для `vacancy_id` нет оффера.
- Первопричина: в системе есть накопленные retry-записи, которые семантически уже неотправляемы из-за отсутствия mapping offer -> vacancy.
- Критичность: `Medium`
- Последствия:
  - шум в логах;
  - ложная нагрузка на цикл;
  - retry queue обрабатывает “безнадёжные” элементы как будто они ещё релевантны.
- Рекомендуемое исправление:
  - различать временный retryable failure и terminal skip condition;
  - вычищать или архивировать retry-элементы без оффера;
  - ввести отдельную причину завершения retry item: `missing_offer_mapping`.

### 3. Итоговая метрика цикла маскирует фактическую деградацию

- Описание проблемы: цикл заканчивается с `Ошибок: 0`, хотя:
  - Sheets phase failed
  - отправка дала `0`
  - retry queue частично прервана по `/stop`
- Первопричина: итоговая агрегирующая метрика не отражает критичность фазовых неуспехов.
- Критичность: `High`
- Последствия:
  - ложная observability;
  - трудно расследовать реальные operational failures;
  - мониторинг может считать run “зелёным”.
- Рекомендуемое исправление:
  - расширить итоговый статус run:
    - `success`
    - `partial_failure`
    - `failed`
    - `stopped`
  - отдельно хранить phase outcomes.

## Подтверждение по коду

Проверка по актуальному snapshot:

- [services/leads_service.py](C:/Users/Арт/Desktop/TrafServer/remote_server_snapshot/services/leads_service.py)
- [utils/database.py](C:/Users/Арт/Desktop/TrafServer/remote_server_snapshot/utils/database.py)

Подтверждено:

1. `upload_sheets(config, leads)` маскирует фазовую ошибку под обычный `0`
- в `services/leads_service.py` исключение внутри выгрузки ловится локально;
- затем функция делает:
  - `logger.error("Ошибка выгрузки в Sheets: ...")`
  - `return 0`
- то есть timeout и “реально нечего добавлять” становятся неразличимыми на уровне вызывающего кода.

2. `run_full_cycle(config, period)` трактует `0` как нормальный результат
- после `added = upload_sheets(config, leads)` код просто пишет:
  - `stats["sheets_added"] = added`
- отдельного признака `sheets_failed` или phase status нет;
- при этом блок после выгрузки продолжает цикл дальше, включая рассылку и retry queue.

3. `run_full_cycle(...)` принудительно завершает run как `ok`
- в конце цикла вызывается:
  - `finish_run(run_id, stats, status="ok")`
- это делается даже если:
  - выгрузка в Sheets падала по timeout;
  - retry queue была прервана по `/stop`;
  - фактический результат частично деградирован.

4. `finish_run(...)` доверяет переданному статусу без дополнительной валидации
- в `utils/database.py` `finish_run(run_id, stats, status="ok")` просто записывает `status` в `run_log`;
- значит источник ложного “зелёного” run — не БД, а вызывающий код в `run_full_cycle`.

5. Retry queue действительно не повышает ошибку уровня цикла сама по себе
- `process_retry_queue(config)` агрегирует только `sent/skipped/errors/duplicates/retried`;
- если отдельные попытки классифицируются как `skipped`, итоговый `errors` остаётся `0`;
- это согласуется с логом, где многократно видно:
  - `[SKIP] ... нет оффера для vacancy_id ...`
  - `Ошибок: 0`

6. Terminal `SKIP` в retry queue могут застревать бесконечно
- `get_due_retries()` выбирает только записи с:
  - `next_retry_at <= now`
  - `retry_count < max_retries`
- `process_retry_queue(config)` для terminal skip:
  - не вызывает `remove_from_retry_queue(...)`
  - не увеличивает `retry_count`
  - не переносит запись на новое `next_retry_at`
- удаление происходит только если запись уже есть в `send_history`;
- значит запись, которая стабильно даёт `SKIP` из-за отсутствующего offer/vacancy mapping, может снова и снова попадать в `due_retries` без естественного завершения.

## Уточнённый вывод

Теперь причина подтверждена не только логом, но и кодом:

- timeout Google Sheets теряется в `upload_sheets()` как обычный `0`;
- `run_full_cycle()` не отличает “ничего не добавили” от “выгрузка сломалась”;
- тот же `run_full_cycle()` в конце всё равно пишет `status="ok"` в `run_log`.
- terminal skip-сценарии в retry queue не имеют корректного завершения и из-за этого могут оставаться вечным operational noise.

То есть первопричина ложного `Ошибок: 0` — это **неудачная модель фазовых исходов**, а не просто один сетевой timeout.
