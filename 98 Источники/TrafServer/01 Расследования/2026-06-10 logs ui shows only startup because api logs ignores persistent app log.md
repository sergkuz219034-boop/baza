# 2026-06-10 logs UI shows only startup because API logs ignores persistent app log

Теги: #debug

## Симптом

В UI при запуске `Полный цикл` пользователь видел только старт запуска и несколько старых строк, но не видел live-ход фазы 1/2/3, хотя worker на сервере продолжал выполнять цикл.

## Зона проекта

- `api/server.py`
- `api/ws_manager.py`
- `traffic_hub/worker.py`
- `utils/database.py`
- `utils/runtime_logging.py`
- Связанные заметки: [[Runtime database]], [[Owner-scoped logs и Google Sheets auth]], [[Leads service]]

## Текущая гипотеза

`GET /api/logs` и UI-логика должны были объединять live `ws_manager` и persistent `app_log`, но frontend фактически подхватывал persistent историю только если окно было совсем пустым. Как только websocket присылал стартовую строку, fallback больше не запускался, поэтому worker-история оставалась скрытой.

## Проверки

### Проверка 1

- Что сделал: посмотрел live-логи `traffichub_worker` во время нового `run`.
- Что ожидал: если логика рабочая, должны идти строки фаз и обработка лидов.
- Что увидел: worker реально выполняет цикл и пишет строки фаз 1/2/3.

### Проверка 2

- Что сделал: проверил таблицу `/app/data/runtime/autolead.db` внутри worker-контейнера.
- Что ожидал: `app_log` должен содержать owner-scoped записи `artem`.
- Что увидел: таблица `app_log` существует и содержит свежие строки `artem` на момент выполнения цикла.

### Проверка 3

- Что сделал: вызвал `api.server.get_logs(lines=5, _user=AccessPrincipal(username="artem", role="user"))` внутри server-контейнера.
- Что ожидал: endpoint должен вернуть свежие строки из persistent `app_log`.
- Что увидел: endpoint уже возвращает live строки `app_log` для `artem`, включая итог цикла.

### Проверка 4

- Что сделал: просмотрел `dashboard/app.js`.
- Что ожидал: fallback истории должен подмешивать persistent лог даже если websocket уже прислал стартовую строку.
- Что увидел: fallback вызывал `loadRecentLogHistory()` только при `!logLines.length`, то есть не работал в самом частом сценарии.

### Проверка 5

- Что сделал: проверил обработчик кнопки `Очистить` в dashboard.
- Что ожидал: кнопка должна вызывать `DELETE /api/logs`, чтобы чистить persistent историю пользователя.
- Что увидел: кнопка вызывала только локальную очистку DOM/массива, без server-side удаления.

## Наблюдения

- `utils/database.py` пишет `app_log` owner-scoped и хранит его постоянно.
- `api/server.py` уже умеет читать persistent `app_log` и очищать его вместе с in-memory cache.
- `dashboard/app.js` был узким местом: persistent history подмешивалась только когда экран был полностью пустым.
- Из-за этого после первого websocket-сообщения (`Новый запуск: run`) дальнейшая persistent история не подтягивалась.
- После дополнительной проверки подтвердилось, что server-side очистка для `artem` реально оставляет `0` строк в `GET /api/logs`.
- Отдельный UX-дефект был в автоскролле: лог принудительно тянул пользователя вниз из-за временного `force-stick` режима.
- Часть low-signal строк попадала в UI даже после owner-scoped фикса, потому что они приходили из live websocket snapshot и не отфильтровывались на этом слое.
- Финальный live-root-cause для повторного появления строк после очистки был не только в backend. Браузер держал старый `ws/log` и старый таймер history fallback, поэтому после `DELETE /api/logs` мог дорисовать поздний ответ от старого запроса.
- В `autolead (9).log` подтвердился второй дефект: часть строк дублировалась во вложенном формате `INFO: 2026-... INFO: ...`, из-за чего обычная дедупликация по `ts/level/msg` не срабатывала.
- На живом сервере источник истины для этой правки оказался в `/root/TrafficHub`, а не во временных правках внутри `/app`. Контейнер пришлось пересобрать именно из server source tree.

## Вывод

Проблема была не в worker и не в сборе/рассылке, а в том, что UI лог-панель неверно синхронизировала persistent историю. Worker-логи существовали в `app_log`, но frontend не докачивал их после первого websocket-сообщения.

Отдельно выяснилось, что кнопка очистки вообще не удаляла persistent `app_log`, поэтому после refresh старые строки возвращались.
Финальная причина “вакханалии” в логах состояла из трёх частей: UI не вызывал server-side clear, автоскролл был слишком агрессивным, а low-signal строки не фильтровались одинаково для persistent и live snapshot.
После live-фикса причина стала уже точечной:
- очистка должна сбрасывать epoch клиентского лога и старый websocket, иначе старые ответы дорисовывают уже удалённые строки;
- сервер должен нормализовать вложенные сериализованные лог-сообщения до канонического вида, иначе дубли проходят как разные записи.

## Следующий шаг

- Оставить `/api/logs` owner-scoped и persistent-first.
- Проверить, что `DELETE /api/logs` очищает и persistent `app_log`, и in-memory cache.
- Поддерживать в UI периодический merge persistent history с live websocket snapshot, а не только одноразовую загрузку.
- Держать в wiki явную пометку, что любые hotfix этой зоны нужно выкатывать в `/root/TrafficHub` и пересобирать `autolead_server_bot`, иначе локальный diff и live runtime разъедутся.
