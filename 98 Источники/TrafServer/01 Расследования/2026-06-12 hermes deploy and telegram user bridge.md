# 2026-06-12 hermes deploy and telegram user bridge

Теги: #debug #архитектура #интеграции

## Симптом

Нужно понять, можно ли поднять Hermes на сервере и сохранить работу через Telegram-аккаунт Виктории "как раньше".

## Зона системы

- Hermes runtime
- Telegram user-session bridge
- server deployment

## Гипотеза

Hermes можно развернуть на сервере как отдельный контейнерный runtime, а Telegram-режим Виктории работает не через bot token, а через Telethon user session. Значит перенос возможен, но только если перенести/создать Telegram-session и обеспечить доступ к `hermes` runtime на той машине, где крутится мост.

- Вместо этого подтверждён рабочий путь через ядро Hermes `run_agent.AIAgent` из `/usr/local/lib/hermes-agent`, которое bridge теперь использует как реальный backend генерации; Python остаётся только транспортным мостом Telethon и таймером ответа.
- Одноразовая серверная проверка `_ask_hermes(...)` на live-окружении вернула уже новый recruiting-ответ по сценариям `Тетрика`, `Т-Банк` и `Воксис`.
- Дополнительный разбор `ChatTG/DataExport_2026-06-02` подтвердил повторяющийся провал старого сценария:
  - `chat_0003/messages.html`: кандидат просит только чаты, дома нет тишины, был негативный опыт с `Воксис`; старый скрипт всё равно вёл в `Воксис`, а потом в московский `Т-Банк`.
  - `chat_0067/messages.html`: старая чат-вакансия + без опыта; старый скрипт слишком быстро падал в общий `онлайн-проект` и затем в `Воксис`, вместо city-first маршрута в `Т-Банк`.
  - `chat_0074/messages.html`: после вопроса `Без звонков?` старый скрипт не умел быстро перестроить оффер под чатовый запрос.
- В `tools/hermes_telegram_user_bridge.py` после этого ужесточены правила:
  - `расскажите подробнее` больше не считается согласием на анкету;
  - добавлены отдельные сигналы `нет тишины`, `старая чат-вакансия`, `уже пробовал Воксис`;
  - при стадии `qualifying` bridge теперь детерминированно добирает только недостающие ответы, а не уходит в модель.
- Подтверждена ещё одна runtime-причина "долгого ответа": debounce-схема сбрасывала таймер на каждый новый короткий месседж кандидата, поэтому серия ответов `по одному сообщению` могла отодвигать реакцию на несколько минут.
- В bridge добавлен capped debounce:
  - базовая задержка сокращена до окна `45-70` секунд;
  - общий потолок ожидания одной серии сообщений ограничен `90` секундами;
  - после деплоя на сервере wrapper снова словил CRLF и путь читался как `hermes_telegram_user_bridge.py\r`; это подтверждено live-логом и исправлено нормализацией LF.
- В отдельном цикле улучшений добавлен offer-transition слой:
  - если кандидат отказывается от `Тетрики`, bridge сразу переводит в `Онекту`;
  - если кандидат отказывается от `Онекты`, bridge сразу переводит в `Т-Банк`;
  - если кандидат отказывается от `Т-Банка`, bridge предлагает `Воксис`;
  - квалификация при этом не запускается заново, если базовые сигналы уже собраны.
- Пользователь отдельно уточнил критичный бизнес-факт, который противоречил части старых заметок и промежуточных формулировок:
  - `Онекта` — это не чатовый формат, а звонковый;
  - `Т-Банк` — это формат `чаты + звонки`, причём условия зависят от региона и строки в xlsx-матрице;
  - чисто чатовых вакансий в текущем наборе нет.
- После этого в bridge и recruiter-vault убраны формулировки, которые подавали `Онекту` как что-то "ближе к чатам", и ужесточён ответ на запросы `только чаты` / `без звонков`: теперь bridge сначала честно проговаривает ограничение, а уже потом предлагает ближайший реальный вариант.
- Отдельно наращён objection-layer по реальным чатам:
  - `это не обман?`, `плохие отзывы`, `боюсь ссылки`;
  - `зачем анкета`, `не хочу оставлять данные`;
  - `я не из РФ`, `не подходит номер/документы`;
  - `почему такая маленькая зарплата`.
- Эти ветки переведены в deterministic-ответы bridge, чтобы они не зависели от свободной генерации и быстрее срабатывали в живом диалоге.
- Следующий слой objection-handling тоже закреплён детерминированно:
  - `я подумаю`, `не сейчас`, `позже`;
  - `зачем в Тетрике указывать цифру 3`;
  - `зачем нужна ссылка на резюме`;
  - `я уже пробовал такую работу, мне не понравилось`.
- Это закрывает типичные точки отвалов перед самой анкетой и уменьшает вероятность, что кандидат "зависнет" без ответа на технический вопрос.
- По следующим реальным кейсам добавлен ещё один слой deterministic-ответов:
  - `chat_0205/messages.html`: кандидат возмущается, что откликался на `оператора чата`, а в ответ приходит звонковая/продажная вакансия;
  - `chat_1678/messages.html` и `chat_1688/messages.html`: кандидат уже заполнил анкету, но с ним не связались;
  - `chat_0003/messages.html`: кандидат прямо пишет, что дома нет тишины и ему неудобны звонки;
  - отдельные кейсы по `самозанятости` и `ТК РФ` подтверждают, что кандидатам важно не общее `уточнят коллеги`, а честная рамка по текущему офферу.
- После этого в bridge добавлены новые быстрые отработки:
  - `самозанятость / ТК РФ / трудовой договор`;
  - `я откликался на чаты, а тут звонки / продажи`;
  - `заполнил анкету, но со мной не связались`;
  - `дома нет тишины / только переписка`.
- Эти кейсы одновременно занесены в recruiter-vault как постоянные заметки `old_chat_vacancy_mismatch.md` и `no_callback_after_form.md`, чтобы retrieval тоже подхватывал их как few-shot паттерны.
- Следующий runtime-провал был уже не в логике маршрутизации, а в человеческом ритме ответа:
  - even после capped debounce live bridge всё ещё ждал базово `45 + jitter`, что на коротких уточнениях выглядело как заторможенный HR;
  - особенно плохо это выглядело на коротких ответах кандидата уровня `да`, `давайте`, `Москва`, `подходит`, когда по смыслу можно отвечать заметно быстрее.
- После этого в bridge добавлен stage-aware быстрый режим:
  - базовая задержка снижена до диапазона `25-37` секунд;
  - общее окно серии сообщений ограничено `45` секундами;
  - для коротких follow-up сообщений на стадиях `qualified / offered / waiting_form` используется отдельный быстрый диапазон около `12-22` секунд.
- Дополнительно добавлена отдельная deterministic-отработка на кейс `в вакансии было написано одно, а по факту другое`, чтобы Hermes не оправдывал старые объявления и не повторял неподтверждённые обещания про `чаты или звонки на выбор`.
- Следом усилен objection-layer ещё для двух живых классов сомнений:
  - `много плохих отзывов`, `пишут что развод`, `видел негатив`;
  - `это продажи?`, `это холодные звонки?`, `нужно обзванивать?`.
- Для них bridge теперь отвечает через vacancy-specific рамку:
  - `Тетрика` — запись на вводный урок, база тёплая;
  - `Онекта` — честно звонковый формат;
  - `Т-Банк` — честно `чаты + звонки`;
  - `Воксис` — звонковая поддержка, но полностью удалённо и со сменами от 4 часов.
- Следующий live-анализ `ChatTG` показал ещё два устойчивых провала старого контура:
  - кандидат спрашивает, почему ему пишут только сейчас и почему старое объявление всё ещё активно;
  - кандидат просит `только чаты` не просто по вкусу, а из-за проблем с речью / невозможности говорить.
- После этого в bridge добавлены:
  - deterministic-ответ на `почему вакансия ещё активна / почему только сейчас написали`;
  - deterministic-стоп на голосовые офферы, если кандидат прямо описывает ограничение по речи и запрос `только чаты`.
- Для retrieval это закреплено отдельными кейсами `stale_old_vacancy_and_late_contact.md` и `voice_constraint_no_calls.md`.
- Отдельный класс ошибок оказался связан не с prompt, а с разбором телеграмных ответов кандидата:
  - ответы по строкам `1/2/3/4/5`;
  - ответы короткими фрагментами через запятую;
  - диапазоны вида `4-5 часов`.
- После этого в bridge добавлены:
  - разбор структурированных ответов по пунктам;
  - fallback-разбор коротких фрагментов по смыслу;
  - корректный парсинг диапазонов часов;
  - запрет на преждевременное согласие на анкету по случайному `да` внутри опроса.
- Дополнительно скорость ответа перестроена по типу сообщения:
  - полный кандидатский ответ на опрос теперь идёт через отдельный `qualified`-delay профиль;
  - objections уровня `плохие отзывы`, `не подходит`, `почему так поздно` тоже больше не ждут длинное базовое окно;
  - server wrapper переведён на более короткое окно ответа `14-22` секунд, а короткие follow-up сообщения стали ещё быстрее.
- Следом подтверждён ещё один практический дефект из live-диалогов:
  - краткий ответ `не было` не распознавался как `нет опыта`;
  - generic-сообщения уровня `привет` могли затирать поле города.
- После фикса:
  - `не было` теперь читается как short-form ответа `нет опыта`;
  - generic ping не попадает в `city`;
  - сценарий `оператор чата -> не было -> Москва` корректно доводит кандидата до оффера `Т-Банк`.
- Отдельно в bridge добавлен `typing`-этап перед отправкой сообщения, чтобы в user-session диалоге от аккаунта Виктории показывался статус печати, а не мгновенный голый send.
- Чтобы эти сценарии не ломались при следующих правках, добавлен локальный `tools/hermes_bridge_selftest.py`, который гоняет ключевые recruiter-кейсы до выкладки на сервер.
- Следующий подтверждённый регресс оказался не в retrieval и не в парсинге, а в самом порядке управления диалогом:
  - bridge вызывал `_deterministic_reply(...)` раньше Hermes runtime;
  - из-за этого стадии `new / qualifying / qualified / offered` частично шли через Python-шаблоны;
  - именно это давало эффект повторения тех же вопросов после уже полученных ответов кандидата.
- После фикса канон изменён на `Hermes-first`:
  - Hermes runtime снова стал основным dialogue brain;
  - deterministic-слой оставлен только для operational-кейсов `waiting_form`, `done`, `ты бот?`, late-contact, voice-constraint и явной отправки анкеты после согласия;
  - в `Chat state` добавлен `missing_answers` и явный запрет повторно спрашивать уже отвеченные поля.

## Вывод

Да, Hermes может работать через Telegram-аккаунт Виктории, но только в режиме user-session:

- нужен `TG_API_ID` и `TG_API_HASH` либо доступный `opente.api`-источник API credentials;
- нужна авторизация по номеру телефона, коду и, если включена, 2FA;
- нужна сохранённая session string;
- мост должен запускаться там, где доступен `hermes` runtime/CLI.

Текущий runtime-вывод:

- сам Hermes gateway на сервере поднят;
- Telegram bridge авторизован и жив;
- фактический recruiting-ответ теперь строится через Hermes runtime `run_agent`, а `FreeLLMAPI` используется как OpenAI-compatible transport под капотом этого runtime;
- отдельный fallback HTTP в bridge сохранён только как запасной контур на случай сбоя импорта runtime.

Если на сервер просто положить container для `hermes-agent`, а Telegram-мост оставить на локальной машине, это уже будет другая схема. Автоматический перенос личной Telegram-сессии без повторной авторизации всё равно не гарантируется.

## Следующий шаг

- Зафиксировать отдельный playbook для server deployment Hermes.
- Следить по живым диалогам, не нужно ли ужесточить словарь распознавания городов и фраз `не хочу звонки`.
- При следующем цикле доработки проверить, нужен ли отдельный state для анти-повторов между несколькими входящими сообщениями в одном окне задержки.
- Нарастить набор `06 Real Cases` ещё на 10-20 диалогов из `ChatTG`, чтобы повысить покрытие возражений по `Тетрике`, `Т-Банку` и `Онекте`.
- Проверить по live-логам, не нужен ли отдельный follow-up шаблон, если кандидат после ручной передачи номера всё равно не получил обратную связь.
- Добрать по live-чатам ещё несколько формулировок возражений вокруг `плохих отзывов` и `холодной базы`, если кандидаты начнут писать их в более разговорном виде.
