# Production env хранится как root-only secret

## Проблема

Production `.env` содержит внутренние shared secrets, DB credentials и внешние credentials. После публикации файла все значения считаются скомпрометированными.

## Контекст

Runtime TrafficHub управляется из `/root/TrafficHub`. `docker compose` требует `.env`, но обычный SSH-пользователь `codex` не имеет sudo. До ротации `.env` был `root:docker 640`, что удобно для compose-операций, но слабее как secret storage.

## Решение

- После ротации хранить production `.env` как `root:root 600`.
- Для maintenance через пользователя без sudo временно использовать root-equivalent Docker-контекст только на время контролируемой операции и возвращать `600`.
- Backup `.env` хранить рядом с production файлом как `root:root 600`, не добавлять в Git и не удалять автоматически.
- Не выводить значения secrets в терминал, wiki, Git diff, логи или отчёты.

## Последствия

- `docker compose config/up` от пользователя `codex` напрямую может не работать, если `.env` недоступен для чтения.
- Это осознанный trade-off в пользу безопасности после компрометации.
- Для следующей ротации нужен playbook временного доступа к `.env` без раскрытия значений.

## Альтернативы

- `root:docker 640`: удобнее для эксплуатации, но любой участник группы `docker` может читать файл.
- Внешний secret manager: правильнее долгосрочно, но сейчас не внедрён и не был частью инцидентной ротации.
