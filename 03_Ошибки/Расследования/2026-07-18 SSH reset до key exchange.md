# 2026-07-18 SSH reset до key exchange

## Симптом

Внешняя автоматизированная среда при подключении к `150.241.70.31:22` получает `kex_exchange_identification: Connection reset by peer` до проверки SSH-ключа.

## Зона системы

- host firewall `ufw`;
- `sshd`;
- Fail2Ban jail `sshd`;
- внешний SSH-клиент с серией коротких соединений.

## Гипотеза

Сброс выполняется до `sshd` правилом `UFW LIMIT` для `22/tcp`, когда один внешний адрес создаёт много коротких соединений за малый интервал.

## Проверка

- Канонический alias `traffichub-live` успешно вошёл пользователем `codex`.
- `fail2ban-client status sshd`: активных блокировок `0`.
- UFW: `22/tcp LIMIT IN Anywhere`, HTTP/HTTPS разрешены.
- Effective sshd: `PubkeyAuthentication yes`, `PasswordAuthentication no`, `PermitRootLogin no`, `MaxStartups 10:30:100`.
- Журнал `sshd` содержит успешные входы тем же ED25519-ключом с нескольких внешних IP, иногда сериями за короткий интервал.
- События проблемной среды могут отсутствовать в journal, если пакет сброшен UFW до передачи управления `sshd`.

## Наблюдение

Ключ корректен, SSH-сервис доступен, Fail2Ban не является текущей причиной. `UFW LIMIT` рассчитан на обычные интерактивные подключения и конфликтует с агентами, создающими много отдельных SSH-сессий.

## Вывод

Наиболее вероятная причина — rate-limit UFW, а не ключ или allowlist. Уверенность высокая, но точный IP проблемной среды не передан, поэтому прямое совпадение с UFW log не подтверждено.

## Следующий шаг

Безопасные варианты:

1. Предпочтительно — разрешить `22/tcp` только для подтверждённых стабильных egress IP и оставить общий `LIMIT`.
2. Если egress IP динамические — заменить общий `LIMIT` на `ALLOW`, сохранив key-only SSH, `PermitRootLogin no` и Fail2Ban.

Перед изменением firewall оставить текущую SSH-сессию открытой, выполнить `sshd -t`, проверить новый вход и публичный `/api/health`.

## Инцидент при изменении UFW

### Симптом

При замене `LIMIT 22/tcp` на `ALLOW 22/tcp` команда `ufw insert 1 allow 22/tcp` сообщила `Skipping inserting existing rule`, потому что UFW посчитал существующий `LIMIT` эквивалентным правилом для проверки дубликата. Следующая команда удалила `LIMIT`; в результате разрешающего правила для порта 22 не осталось.

### Наблюдение

- Установленная SSH-сессия сохранилась до завершения команды и позволила увидеть итоговый `ufw status`.
- Новый SSH-вход получает reset от UFW.
- Альтернативные SSH-порты не настроены.
- Provider: AS215439 PLAY2GO INTERNATIONAL LIMITED; локальных provider API credentials нет.

### Вывод

Последовательность `insert allow` → `delete limit` небезопасна: сообщение `Skipping` должно считаться ошибкой, а не успешным добавлением.

### Восстановление

Через web/VNC-консоль провайдера выполнить:

```bash
sudo ufw allow 22/tcp comment 'SSH key-only automation'
sudo ufw status verbose
```

После восстановления проверить новый SSH-сеанс, `sshd -t`, Fail2Ban и `/api/health`.

### Постоянное правило процедуры

Перед удалением старого firewall-правила обязательно проверять наличие нового правила в фактическом `ufw status numbered`. Если UFW пишет `Skipping`, старое правило не удалять. Для смены action на том же порту предпочтительно использовать provider console или временное правило с ограничением по конкретному source IP, которое UFW не считает дубликатом.

## Итоговое исправление

### Проверка после восстановления

- Новый SSH-сеанс снова входит как `codex`.
- UFW разрешает 22 и 2222 для IPv4/IPv6; default incoming остаётся `deny`.
- `PermitRootLogin no`, `PasswordAuthentication no`, `AuthenticationMethods publickey` подтверждены через `sshd -T`.
- Fail2Ban активен, текущих banned IP после проверки нет.
- `/api/health` вернул `status=ok`.

### Дополнительное наблюдение

После удаления UFW rate-limit прямые серии соединений всё равно иногда получали reset, причём неуспешные попытки отсутствовали в journal `sshd`. Перенос на 2222 сам по себе также не устранил транспортные сбросы. Следовательно, UFW был не единственной причиной; часть reset происходит до регистрации сессии сервером.

### Решение

- `sshd` слушает 22 и 2222; automation alias использует 2222, порт 22 оставлен fallback.
- Ubuntu `ssh.socket` отключён, `ssh.service` включён напрямую, иначе второй порт не открывался.
- `LoginGraceTime` снижен до 30; очередь увеличена до `MaxStartups 50:30:200`; установлен `PerSourceMaxStartups 20`.
- Канонический `ssh_live_bash.ps1` получил до 8 повторов только до remote ready-marker. После marker повтор запрещён, поэтому мутации не дублируются.

### Доказательство

- Wrapper: `20/20` успешных коротких подключений.
- Проверка защиты от повторного выполнения: удалённый `exit 7` вернул код `7` без повторного запуска.
- Оба порта слушают IPv4 и IPv6; `sshd -t` успешен; health зелёный.

## Переносимый быстрый доступ

### Симптом

Обычный вызов `ssh` из внешней Windows-среды прекращает работу после первого случайного reset до key exchange. После распаковки ZIP Windows также может добавить приватному ключу наследуемые ACL, из-за чего OpenSSH отклоняет ключ как `UNPROTECTED PRIVATE KEY FILE`.

### Решение

- Локально собран `TrafficHub_SSH_Quick_Access.zip` с `connect.cmd`, `connect.ps1` и действующим ключом `codex`.
- Коннектор чередует порты 2222 и 22 и повторяет только SSH-завершения с кодом 255; штатный выход с сервера завершает launcher.
- Перед соединением launcher удаляет наследуемые ACL ключа и оставляет чтение текущему пользователю, `SYSTEM` и локальным Administrators через language-neutral SID.
- Исполняемый PowerShell-файл содержит только ASCII, чтобы одинаково разбираться Windows PowerShell 5 и PowerShell 7 без зависимости от BOM.

### Проверка

Архив распакован в новый каталог и запущен с `-Probe`: ключ принят, на `150.241.70.31:2222` получен маркер `quick-access-ok`, exit code `0`.

### Риск

ZIP содержит приватный SSH-ключ и должен считаться секретом: его нельзя публиковать, помещать в Git или передавать посторонним.

## Сверка серии из 12 неуспешных попыток

### Проверка

- UFW: `22/tcp ALLOW`, `2222/tcp ALLOW`; kernel log не содержит `UFW BLOCK`/`UFW LIMIT` для источника `50.7.157.42`.
- Fail2Ban: `Currently banned: 0`; в `fail2ban.log` нет действий по `50.7.157.42`.
- `sshd` слушает оба порта; effective key-only policy и увеличенная pre-auth очередь активны.
- Journal содержит ровно 12 записей `Connection closed by authenticating user codex 50.7.157.42 ... [preauth]` с `12:28:16Z` по `12:28:55Z`.
- После исправления ACL распакованного ключа тот же источник и тот же fingerprint успешно авторизовались в `12:29:25Z`, `12:34:29Z` и `12:35:31Z`.

### Вывод

Эта конкретная серия из 12 попыток не была сброшена firewall, Fail2Ban или серверным allowlist. По серверному журналу клиент сам закрыл соединения до auth; локальная проверка связала серию с первой распакованной версией архива, в которой OpenSSH отклонил ключ из-за слишком широких ACL. Текущий архив исправляет ACL до запуска `ssh.exe` и подтверждён успешным входом.
