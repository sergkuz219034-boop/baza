## Высокая важность

### H1. Telegram-рассылки доступны без проверки роли и владельца

**Доказательства:** `api/server.py:408`, `:411`; `api/routers/telethon_mailing.py:140`, `:534`, `:568`, `:595`. Подключение router защищено общей аутентификацией. Запросы аккаунтов, кампаний и получателей глобальные; запуск и остановка не проверяют владельца или административную роль.

**Условие:** обычный лицензированный пользователь обращается непосредственно к API. **Последствие:** доступ к общим получателям и аккаунтам, возможность запускать или останавливать чужие кампании с общими Telegram-сессиями. Факт эксплуатации не установлен.

**Исправление:** административный доступ для общей функции либо модель владельца/tenant с обязательной фильтрацией всех чтений и действий.

### H2. Остановка основного задания не останавливает отправки RU worker

**Доказательства:** `traffic_hub/worker.py:212`, `:432`; `traffic_hub/services/remote_autolead.py:192`, `:323`; `traffic_hub/remote_worker.py:160`. Origin прекращает свой subprocess, но удалённый heartbeat не проверяет остановку родителя; локальные stop flags удалённого worker сбрасываются, Redis-состояние отключено.

**Условие:** остановка после передачи удалённого пакета. **Последствие:** внешние отправки продолжаются после остановки в интерфейсе; старое задание может мешать следующему.

**Исправление:** отмена удалённых задач по parent ID и проверка состояния родителя при heartbeat и перед отправкой.

### H3. На RU worker игнорируются накопленные дневные лимиты

**Доказательства:** `traffic_hub/remote_worker.py:107` возвращает ноль из `get_daily_sends` и `get_daily_offer_sends`; `modules/vbiv_bot.py:1444`, `:1007`, `:1633`; `traffic_hub/job_runner.py:177`. Каждый новый пакет начинает счётчик заново.

**Условие:** включены дневной лимит/цель, обработка идёт несколькими удалёнными пакетами либо ранее уже были отправки. **Последствие:** превышение пользовательского ограничения.

**Исправление:** канонические суточные счётчики и резервирование остатка на origin, передача остатка и учёт отправок внутри пакета.

### H4. Ошибка чтения истории разрешает повторные внешние отправки

**Доказательства:** `traffic_hub/job_runner.py:92` перехватывает ошибку snapshot/history и заменяет историю на `{}`, после чего `:181` продолжает dispatch; `traffic_hub/remote_worker.py:100`; `modules/vbiv_bot.py:916`, `:1467`.

**Условие:** временная ошибка БД при загрузке истории уже обработанных анкет. **Последствие:** ранее отправленная анкета снова допускается к отправке. Уникальность записи после внешней отправки не предотвращает саму отправку.

**Исправление:** при недоступной истории приостанавливать/перепланировать пакет, а не считать историю пустой.

### H5. Сервер уже испытывал OOM с остановкой Redis и приложения

**Доказательства runtime:** журнал ядра 2026-10-07 около 00:43 МСК (2026-10-06 21:43 UTC): global OOM убил `chrome-headless` и `redis-server`; memory cgroup OOM убил Python приложения с RSS около 2 ГБ. `traffichub_app` имеет `OOMKilled=true`. Снимок: RAM 3915 MiB, доступно 653 MiB; swap использован 2364 из 2559 MiB. У worker `Memory=0`, ограничение отсутствует; `docker-compose.yml:131`.

**Последствие:** сбои приложения и очередей под нагрузкой. На момент проверки health приложения отвечал успешно; постоянный текущий outage не утверждается. Точный инициатор всей нагрузки не установлен.

**Исправление:** общий бюджет памяти для контейнеров, ограничения worker/browser concurrency, профилирование потребления и оценка необходимой ёмкости сервера.

## Средняя важность

### M1. Telegram-кампания не возобновляется после перезапуска API

`api/routers/telethon_mailing.py:25` хранит задачи только в памяти; `:573` возвращает уже существующее состояние `running` без создания новой задачи. После перезапуска процесс задачи исчезает, состояние остаётся. Нужны восстановление состояния при старте и durable executor либо явный перевод прерванных кампаний в состояние для возобновления.

### M2. Пауза Telegram оставляет получателя в `sending`

`api/routers/telethon_mailing.py:648` сохраняет `sending` перед внешней отправкой `:653`; пауза отменяет задачу `:606`; `CancelledError` заканчивает её без восстановления `:667`. Возобновление выбирает только `pending` (`:631`). Получатель зависает, а результат отправки может быть неизвестен. Требуются состояние неопределённого результата и сверка; слепой повтор опасен дубликатом.

### M3. Access и refresh JWT взаимозаменяемы

`traffic_hub/api/routers/auth.py:33`, `:216`, `:245`, `:249`; `traffic_hub/api/deps.py:106`. Токены имеют одинаковый формат `{sub, exp}` без типа, а проверки не различают назначение. Access принимается для обновления, refresh — как access. Logout (`auth.py:345`) только удаляет cookies. При утечке действующего токена короткая сессия может продлеваться; серверного отзыва нет. Нужны тип токена, отдельные проверки, ротация refresh и отзыв сессии. Утечка не установлена.

### M4. Пользователь с двумя tenant memberships получает ошибку CRM

`traffic_hub/api/deps.py:30` выбирает все memberships и вызывает `scalar_one_or_none()` без ограничения. `traffic_hub/models/database.py:124` допускает членство в разных tenants. При двух строках возникает `MultipleResultsFound` и HTTP 500. Нужен явный выбор активного tenant либо согласованная политика выбора одной записи. Наличие такого пользователя в production не проверялось.

### M5. Параллельные изменения настроек затирают друг друга

`utils/control_store.py:707` читает профиль вне транзакции записи и заменяет весь `config_json`. Независимые writers: `services/source_control.py:30`, `services/autolead_bridge.py:150`, `services/integrations.py:198`. Одновременные изменения разных разделов допускают lost update. Нужны блокировка/ревизия или атомарное обновление отдельных JSONB-разделов.

### M6. Ошибка сохранения оффера выдаётся за успешное сохранение

`services/leads_service.py:1203` подавляет ошибку `save_user_config`, пишет локальный fallback/cache и возвращает штатно; создание/удаление офферов использует этот путь (`services/autolead_bridge.py:152`, `:164`). При отказе БД интерфейс получает успех, но канонический профиль не изменён. В owner context ошибка должна возвращаться вызывающему коду. Межпользовательская утечка через fallback в текущем runtime не подтверждена.

### M7. Ошибки сохранения интеграций также скрываются

`services/integrations.py:196` ловит ошибки чтения/сохранения профиля и только логирует их; callers `:1081`, `:1150` не получают явного результата отказа. При ошибке БД настройки/credentials не сохраняются, несмотря на нормальный ответ. Нужно распространение ошибки или обязательная проверка результата.

### M8. CI падает на контракте главной страницы

Run `37528525371`, PR #256: `tests/test_landing_routes.py:14` ожидает `<title>ТраффикХаб`, а `dashboard/landing.html:2` содержит `<title>TrafficHub — больше откликов, меньше ручной работы</title>`. Итог scoped CI: **1 failed, 98 passed, 1 skipped**. Доказательство: соседний файл `ci-256-failed.log`. Это блокирует зелёную проверку, но не доказывает неисправность самой главной страницы. Нужно согласовать тест с утверждённым контрактом.

### M9. Production, origin/main и штатный deployment расходятся

Серверный main опережает `origin/main` на 25 commits. Origin SHA: `bf55a40259027a54d1036109bbdf041c07f99183`. Live images: `traffichub-runtime-lease:app-result-20261006` и `traffichub-runtime-lease:worker-20261006`; используется дополнительный override `/home/codex/remote-lease-release-20261006/runtime-override.yml`. Обычный `docker compose config` выбирает image с origin SHA. SHA256 `remote_autolead.py` в worker отличается от текущего исходника; в app совпадает. Само различие не доказывает конкретный отсутствующий фикс.

**Последствие:** повторный deployment без внешнего override может вернуть старую версию; Git HEAD не полностью описывает runtime. Нужен единый версионированный manifest и immutable images для согласованного, прошедшего CI релиза.

## Низкая важность

### L1. Пересборка одного commit не воспроизводит зависимости

В `requirements.txt` многие зависимости заданы через `>=`; Dockerfile устанавливает их напрямую и использует тег `python:3.11-slim` без digest. Разные сборки могут получить разные версии. Это риск воспроизводимости, а не подтверждённая CVE. Нужны lock/constraints, hashes и согласованные версии browser/runtime.

### L2. Недостаточный запас диска

Runtime: root volume 119 ГБ, использовано 99 ГБ, доступно около 14 ГБ, заполнение 89%; inodes 18%. Сборки и логи могут исчерпать остаток. Факт ENOSPC не обнаружен. Нужны политика хранения и контроль роста; очистка в рамках аудита не выполнялась.
