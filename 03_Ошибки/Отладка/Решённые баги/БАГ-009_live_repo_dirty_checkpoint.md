# БАГ-009: live-репозиторий `/app` в контейнере был грязным

## Симптом

В контейнере `autolead_server_bot` рабочее дерево `/app` содержало большой набор `tracked`-изменений, удалений старой wiki и временных backup-файлов.

## Зона системы

- live-контейнер `autolead_server_bot`
- git checkout в `/app`
- dashboard/runtime/wiki слой внутри контейнера

## Гипотеза

`/app` не смонтирован с host-репозитория, а живёт во writable-layer контейнера. Поэтому все live-правки накапливались прямо внутри контейнера и оставались незакоммиченными.

## Проверка

- `docker inspect autolead_server_bot` показал bind-mount только для `data/*` и `secrets`, но не для исходников `/app`.
- `git status --short` внутри `/app` показал десятки `M`/`D` по коду и wiki.
- untracked backup-файлы были удалены отдельно.

## Наблюдение

Основная грязь была не мусором, а реальным рабочим слоем:

- live-фиксы dashboard/admin/platforms;
- удаление старой wiki-структуры;
- добавленный migration script `AccountManager/tools/migrate_sqlite_to_postgres.py`.

## Вывод

Для безопасной очистки нельзя было делать `reset --hard`, потому что это бы уничтожило live-фиксы. Канонический безопасный шаг:

- создать локальную ветку-чекпоинт;
- закоммитить текущее состояние;
- получить чистое рабочее дерево без потери runtime-изменений.

На live создана ветка `live-checkpoint-20260618` и commit `e7d0253`.

## Следующий шаг

- Не использовать `/app` внутри контейнера как долгоживущий основной git checkout.
- Канон: хранить исходники в отдельном host-репозитории, а контейнер пересобирать из него.
