# Рецепт отладки

Главный документ метода отладки для `TrafficHub`.

Перед началом использовать общий рабочий маршрут: `[[01_Правила/ИИ/Workflow Codex для дебага и разработки]]`.

## Шаг 0. Зафиксировать симптом

- что сломано
- где видно
- для какого owner/user/тенанта
- является ли симптом owner-specific или затрагивает общий кодовый путь; по умолчанию считать общим, пока не доказано обратное

## Шаг 1. Определить зону системы

- web/ui
- API
- auth
- worker
- runtime store
- БД
- интеграция
- host/deploy

## Шаг 2. Проверить runtime

- `api/health`
- контейнеры
- логи
- heartbeat
- runtime файлы
- env/config markers
- если симптом похож на scheduler, отдельно различить web-loop и worker-loop
- для багов заполнения офферов отдельно выполнять DOM-debug реального browser-path:
  брать owner-scoped `offer_mapping`, актуальный `vbiv.form_proxy_url`, прогонять `enabled` и `disabled` офферы;
  на ошибке сохранять `final_url`, `title`, `body` snippet и screenshot, чтобы отделить timeout, proxy/VPN-detected, disabled landing и валидацию формы.

## Шаг 3. Проверить код

- точку входа
- router/service path
- runtime store boundary
- known invariants
- для worker-path смотреть `traffic_hub/worker.py`
- для hourly `partner_sync` смотреть `api/server.py`, а не очередь worker

- [[03_Ошибки/Отладка/Воркараунды|Воркараунды]]

## Шаг 5. Зафиксировать результат

- Симптом
- Зона системы
- Гипотеза
- Проверка
- Наблюдение
- Вывод
- Следующий шаг

## Шаг 6. Проверить распространение фикса

- если изменены `modules/platforms/*`, `modules/vbiv_bot.py`, очереди, runtime store, settings или deploy, фикс обязан работать для всех пользователей;
- подтвердить, что изменение не завязано на `admin` или конкретный owner;
- подтвердить общий deploy-контур: commit/push, зелёные GitHub checks, rebuild/recreate общего контейнера, live `/api/health`;
- если нужна owner-specific миграция данных, явно указать это в баг-заметке и выполнить её для всех затронутых users.

## Канон фиксации

- каждый нетривиальный баг должен попадать либо в `Активные баги`, либо в `Решённые баги`;
- если проблема расследована глубже root-слоя, нужно связать root-note с archive/investigation note;
- вывод без runtime-evidence считается гипотезой, а не завершённым расследованием.
