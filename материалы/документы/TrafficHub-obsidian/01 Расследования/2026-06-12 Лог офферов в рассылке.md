# 2026-06-12 Лог офферов в рассылке

## Симптом

- в live-логе рассылки строка по лиду показывала только `Офферов найдено: 1`;
- пользователь не видел, какой именно оффер выбран для лида;
- при нескольких офферах лог тоже был слабым для диагностики.

## Зона системы

- `modules/vbiv_bot.py`

## Гипотеза

- строка лога строилась только из `len(matched_offers)` без перечисления `offer.name`;
- при одном оффере сообщение выглядело формально корректным, но бесполезным.

## Проверка

- найдено место формирования строки:
  - `modules/vbiv_bot.py: print(... Офферов найдено: {len(matched_offers)})`
- после правки на production выполнен короткий runtime `send` для owner `debuglogs`;
- подтверждён новый `app_log`:
  - `[1/101] Камилла Салахова | 9953632621 | Оффер: Онекта (1)`

## Наблюдение

- теперь лог показывает:
  - один оффер: `Оффер: <name> (1)`
  - несколько офферов: `Офферы: <name1>, <name2> (...)`
  - если часть офферов уже в истории, добавляется хвост `к обработке: N`
- при этом live-UI не обязан показывать все промежуточные строки:
  - строки выбора лида вида `[1/101] ... | Офферы: ...`
  - строки процесса `-> Заполняем: ...`
  - можно скрывать на уровне `utils/runtime_logging.py`, оставляя в UI только итог:
    - `[OK] Оффер ... успешно заполнен!`
    - `[~] Оффер ... (дубль)`
    - ошибки и статусы задачи

## Вывод

- проблема была не в матчинге офферов, а в бедном формате диагностического лога;
- исправление формата уже раскатано на production и подтверждено runtime-проверкой;
- для UI-ленты отдельное решение: оставлять короткие business-events, а промежуточную детализацию считать шумом.

## Следующий шаг

- если лог станет слишком длинным при большом числе офферов, ограничить вывод, например первыми 3 именами + `…`.
