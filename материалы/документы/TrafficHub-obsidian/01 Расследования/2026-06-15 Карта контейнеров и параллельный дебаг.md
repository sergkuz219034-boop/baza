# 2026-06-15 Карта контейнеров и параллельный дебаг

## Симптом

- Нужно быстро понять:
  - какие контейнеры реально живут на host сейчас;
  - какие из них относятся к TrafficHub;
  - как нескольким разработчикам одновременно дебажить разные части системы без взаимной порчи runtime.

## Зона системы

- Docker runtime на host `150.241.70.31`
- compose-контур `/root/TrafficHub/docker-compose.yml`
- developer workflow для live-debug

## Гипотеза

- Основная проблема параллельного дебага не в том, чтобы “всем зайти на сервер”, а в том, чтобы:
  - развести ownership по контейнерам и debug-owner'ам;
  - не смешивать production traffic и smoke/debug actions;
  - не ломать друг другу browser/session/runtime state.

## Наблюдение

- Для TrafficHub нужно отделять:
  - проектные compose-контейнеры;
  - посторонние host-контейнеры;
  - случайные orphan/container leftovers (`laughing_diffie`).
- Самый конфликтный live-debug слой:
  - `autolead_server_bot`
  - `traffichub_worker`
  - общие Redis keys `traffic_hub:jobs:*`
  - общий PostgreSQL runtime
- Наименее конфликтный слой:
  - `license_auth`
  - `license_server`
  - `account_manager`
  - `caddy`
  - read-only inspection `postgres` / `redis`

## Вывод

- Параллельный дебаг несколькими разработчиками безопасен, если делить работу по слоям:
  - один человек — web/API layer;
  - один — worker/jobs;
  - один — БД/Redis observability;
  - один — auth/license/account_manager;
  - один — reverse proxy / edge.
- Для активных job-run smoke обязательно использовать только debug-owner'ов, а не `admin/alex/...`.

## Следующий шаг

- Держать отдельный playbook по “owner allocation” для live smoke.
- Если будет постоянная командная работа на host, добавить явную таблицу:
  - developer -> container -> owner -> допустимые действия.
