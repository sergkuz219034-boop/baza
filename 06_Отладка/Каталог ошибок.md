# Каталог ошибок

## Что сюда входит

- повторяемые runtime/business/infra ошибки
- типовые симптомы
- первый known-good check

## Минимальный формат записи

- симптом
- затронутый слой
- первый check
- confirmed cause или статус `гипотеза`
- ссылка на расследование или баг-заметку

## Когда обновлять

- когда ошибка повторяется больше одного раза;
- когда найден новый быстрый discriminating check;
- когда старый воркараунд больше не соответствует live системе.

## Повторяющаяся ошибка мышления

### Симптом

- инженер или агент видит `autolead.db` или `control.db` и делает вывод, что live runtime сейчас работает через SQLite.

### Затронутый слой

- runtime diagnosis
- storage boundary
- incident triage

### Первый check

- проверить `docker-compose.yml` и effective env:
  - `AUTOLEAD_RUNTIME_LOGS_BACKEND`
  - `AUTOLEAD_RUNTIME_DELIVERY_BACKEND`
  - `AUTOLEAD_RUNTIME_LEADS_BACKEND`
  - `AUTOLEAD_RUNTIME_AUTOFIT_BACKEND`
  - `AUTOLEAD_RUNTIME_INVITES_BACKEND`
  - `AUTOLEAD_RUNTIME_CONTROL_SYNC_BACKEND`
- проверить, какой backend возвращает `control_store` status;
- отделить `autolead runtime`, `control_store` и `traffic_hub` product DB.

### Confirmed cause

- в текущем live-контуре SQLite-артефакт может быть compatibility/fallback/legacy слоем, а не production source of truth.

### Ссылка

- [[материалы/документы/TrafficHub-obsidian/01 Расследования/2026-06-17 Remaining SQLite surface после PostgreSQL-first runtime]]

## Повторяющаяся ошибка чтения тестов

### Симптом

- инженер смотрит на `sqlite+aiosqlite` или `sqlite3` в `tests/*` и делает вывод, что live backend по-прежнему должен быть SQLite.

### Затронутый слой

- test interpretation
- runtime diagnosis
- architecture understanding

### Первый check

- отделить test fixture backend от live backend;
- проверить live `docker-compose`, env и runtime health;
- выяснить, какой именно сценарий доказывает конкретный тест: migration regression, tenant isolation, router logic или legacy compatibility.

### Confirmed cause

- SQLite в тестах в основном используется как быстрый isolated backend и не является source of truth о текущем production storage contract.

## `leadsu: кнопка submit не найдена`

### Симптом

- в live-логах `Воксис` / `leads.su` появляется `кнопка submit не найдена`;
- затем ошибка помечается как permanent `form-failure`.

### Затронутый слой

- Playwright form-fill
- `modules/platforms/leadsu.py`

### Первый check

- открыть последний `debug_Воксис_*.html` из runtime debug-артефактов;
- если файл имеет размер около `39` байт и содержит пустой `body`, проблема не в селекторе кнопки, а в blank-page contour до submit.

### Confirmed cause

- runtime blank page перед submit;
- recovery должен пытаться не только `reload`, но и повторный `goto(target_url)`.

## `leadsu/vkusvill: форма не подтверждена после отправки`

### Симптом

- `ВкусВилл` в live-логах падает с `форма не подтверждена после отправки`;
- retry queue помечает ошибку как permanent `form-failure`.

### Затронутый слой

- Playwright form-fill.
- `modules/platforms/lovko.py`.
- browser proxy routing в `modules/vbiv_bot.py`.

### Первый check

- открыть свежие `/root/TrafficHub/data/debug/debug_ВкусВилл_*.html` и `.png`;
- проверить, есть ли validation `Укажите город трудоустройства`;
- проверить hidden `input[name="CITY"]`;
- проверить, что `vkusvill.ru` попадает в browser proxy routing при сохранённом proxy URL.

### Confirmed cause

- ВкусВилл принимает только город из своего списка; текст в input без выбора элемента dropdown оставляет `CITY` пустым.
- Если город лида пустой или неподдерживаемый, безопасный fallback — `Москва`.

### Ссылка

- [[06_Отладка/Решённые баги/БАГ-028_vkusvill_city_proxy_fallback]]

## `Отработанная таблица: +0; основная таблица: статусы обновлены у N строк`

### Симптом

- В полном цикле видна строка `Отработанная таблица: +0; основная таблица: статусы обновлены у N строк`.
- Выглядит как ошибка, хотя красного exception нет.

### Затронутый слой

- Full cycle.
- Google Sheets: основная таблица и отработанная таблица.
- `services/leads_service.py`, `modules/sheets_sync.py`.

### Первый check

- Проверить, что строки основной таблицы получили непустой `Статус`.
- Проверить, что `load_pending_leads_for_send()` больше не выбирает эти строки.
- Проверить retry queue по owner: active rows должны быть пустыми или объяснимыми.

### Confirmed cause

- Старый текст лога смешивал два разных действия: новые строки в отработанной таблице и закрытые статусы в основной таблице.
- `+0` допустимо, если результаты были `error/no_offer/no_phone` или уже были в отработанной таблице.
- `pending/processed` — только внутренние имена в коде/API, не пользовательские названия.

### Ссылка

- [[06_Отладка/Решённые баги/БАГ-029_pending_status_log_not_error]]

## Full pytest импортирует `api/services/utils` из `AccountManager`

### Симптом

- `pytest -q` падает на collection;
- ошибки указывают на `/app/AccountManager/api`, `/app/AccountManager/services` или `/app/AccountManager/utils`;
- целевые тесты TrafficHub при этом проходят.

### Затронутый слой

- test isolation
- import path
- вложенный контур `AccountManager`

### Первый check

- искать в новых тестах top-level `sys.path.insert(0, AccountManager)` или удаление repo root из `sys.path`;
- проверить, не импортируются ли short modules `api`, `services`, `utils`, `config`, `database` на уровне module import;
- прогнать полный suite внутри контейнера, а не в неполной локальной Python-среде.

### Confirmed cause

- тест AccountManager загрязнил общий процесс pytest и переключил short-imports основного TrafficHub на одноимённые пакеты AccountManager.

### Ссылка

- [[06_Отладка/Решённые баги/БАГ-026_accountmanager_test_import_pollution]]

## Partner sync: `postback_logs.tenant_id` NULL

### Симптом

- в `docker logs autolead_server_bot` есть `NotNullViolationError`;
- текст: `null value in column "tenant_id" of relation "postback_logs" violates not-null constraint`;
- после этого `TrafficHub: leadsu sync failed for <user>` и `TrafficHub: lovko sync failed for <user>`.

### Затронутый слой

- embedded TrafficHub integrations sync.
- `traffic_hub/api/routers/integrations.py::_import_network_conversions`.
- PostgreSQL table `postback_logs`.

### Первый check

- проверить, передаёт ли путь создания `PostbackLog` поля `tenant_id` и `owner_username`;
- сравнить с корректным путём `traffic_hub/api/routers/postbacks.py::_handle_postback`;
- проверить live `information_schema`: `postback_logs.tenant_id nullable=NO`.

### Confirmed cause

- partner sync path создаёт `PostbackLog` без tenant/owner context, а live DB уже требует `tenant_id NOT NULL`.

- [[01_Расследования/2026-06-23 TrafficHub full senior audit]]
