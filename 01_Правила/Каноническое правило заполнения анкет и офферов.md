# Каноническое правило заполнения анкет и офферов

## Статус

Канон для всех production-офферов. Проверен на live runtime: 2026-08-14. Связано с [[2026-08-09 Tetrika DOM отправка и preview tracking]].

## Owner-scoped mapping

Каждый оффер живёт в `offer_mapping` своего owner. Его минимальный контракт: `name`, `target_url`, `platform`, `enabled`, `vacancy_ids`, опционально `daily_limit`.

- `enabled=false` — оффер не участвует в подборе, отправке и retry; это не ошибка и не «готов к проверке».
- Непустой `vacancy_ids` — отправлять только лиды из этих вакансий.
- Пустой `vacancy_ids` — явный режим «на любую подходящую вакансию»; разрешён только если это отмечено в карточке оффера. Для Тетрики это текущий режим.
- `daily_limit` ограничивает успешные отправки конкретного оффера; общий `daily_goal` ограничивает успешные отправки owner в целом. Лиды сверх лимита остаются в очереди следующего дня.
- URL и credentials никогда не копируются между owner без явной настройки: config, history и retry queue owner-scoped.

## Допуск оффера в поток

Оффер разрешено включать только после ручного контрольного заполнения через DOM.

Обязательные условия:

1. Используется реальная partner tracking URL.
2. URL и redirect не содержат `mode=view`, `{preview_mode:*}`, `aff_id=0` или другого preview-маркера.
3. После redirect существует непустой уникальный tracking ID/click ID.
4. Селекторы привязаны к `name`, `id`, `label`, `placeholder` или семантической роли, а не к позиции элемента.
5. Заполняются только видимые элементы активной формы. Скрытые mobile/desktop-дубли не трогаются.
6. Кандидат имеет валидные телефон, email и resume URL. Для Rabota.ru допустим только `https://www.rabota.ru/resume-search/<id>/?source=response&vacancy_id=<id>&response_id=<id>`.
7. Опыт продаж/контакт-центра для HR-форм передаётся только целым числом месяцев: `6`, `12` и т. п.; строка «6 месяцев» недопустима. Для Тетрики минимум — `6`.
8. Неизвестный пол нормализуется до согласованного default до открытия формы; пол не должен блокировать оффер без такого поля.

## DOM-заполнение

1. Открыть partner tracking URL и дождаться `domcontentloaded` плюс стабилизации формы.
2. Найти видимую форму и построить карту полей: имя, ФИО, телефон, email, resume, дата рождения, опыт, город, гражданство, согласие.
3. Заполнять через DOM-события браузера (`fill`, `selectOption`, `check`), чтобы сработали маски и validators.
4. Перед submit прочитать `FormData` активной формы и проверить нормализованные значения.
5. Нажать видимую submit-кнопку один раз. Повтор запрещён до доказанного отказа первой попытки.

## Доказательство успеха

Статус `Отправлено` допустим только при одновременном выполнении:

- advertiser form endpoint вернул HTTP `2xx`;
- виден success-state: modal/success box/redirect с текстом принятой заявки;
- отсутствует validation error;
- tracking ID реальный, не preview placeholder;
- сохранены timestamp, offer ID, endpoint/status и screenshot без публикации PII.

Одного исчезновения формы, клика submit, отсутствия исключения Playwright или текста в логах недостаточно.

## Ошибки

- `invalid_tracking_link` — preview URL, placeholder click ID, `aff_id=0`.
- `field_not_found:<field>` — обязательное поле не найдено в видимой форме.
- `validation_failed:<field>` — форма отклонила значение.
- `submit_http:<status>` — endpoint вернул не-2xx.
- `success_state_missing` — endpoint ответил, но UI не подтвердил приём.
- `tracking_not_confirmed` — advertiser принял форму, но партнёрская атрибуция не доказана.

### Retry-классификация

- Неполные или невалидные данные кандидата, отключённый оффер и preview-link — terminal: не повторять до изменения данных/настройки.
- Сеть, proxy, timeout и временная partner error — retry с ограничением; новый submit только после duplicate-check.
- `form was not confirmed after submit` — не считать отправкой; сначала проверить success-state и partner history, затем повторять только безопасно.
- Каждый retry обязан сохранять только код причины и correlation ID; не сохранять PII в ошибке.

## Канон по платформам

### LeadSU / Тетрика

`platform=leadsu`, но маршрут должен определяться и после redirect по имени оффера или домену `tetrika-school.ru`.

- Нужны ФИО из минимум двух частей, нормализованный телефон и реальный email.
- Поле опыта принимает число месяцев, для Тетрики — не меньше `6`; если значение взято из резюме, в payload передаётся только цифра.
- Заполняются только видимые Tilda-controls на странице; скрытые desktop/mobile-дубли игнорируются.
- Успех — только видимый `.t-form__successbox` либо равнозначное подтверждение партнёра. Отсутствие такого state создаёт retry, не `sent`.

### Lovko / browser offers

Перед запуском обязательна доступность form-proxy и RU-проверки. Ошибка proxy (например, `ERR_CONNECTION_RESET`) означает состояние `degraded`: очередь сохраняется, новые попытки не должны маркироваться как отправленные.

Для каждого Lovko-оффера применяются общие правила visible form, duplicate-check, лимиты и success-state. Смена landing или redirect требует повторной стабилизации.

## Стабилизация

Оффер считается стабильным после трёх последовательных успешных DOM-тестов на разных тестовых кандидатах без изменения селекторов, с реальным tracking ID. После изменения landing page, redirect, полей или endpoint стабилизация повторяется.

## Запреты

- Не считать preview submission партнёрской конверсией.
- Не обновлять лид как `Отправлено` до всех success-инвариантов.
- Не повторять submit после timeout без проверки, не принял ли endpoint первую попытку.
- Не логировать полный email, телефон, resume URL или HTML с PII.

## Канонический контроль каждого пресета — 2026-10-09

Прямое указание пользователя: выбирать необработанного лида из таблицы по подходящей вакансии, проверять работоспособность пресетов, сохранять подтверждения и публиковать проверенные знания в канонической wiki `baza`.

1. Получить полный актуальный список `#om-preset` и все варианты роли. Для Lovko использовать URL подключённого owner/publisher, не общий шаблон чужого publisher.
2. Сначала проверить из рабочего RU-контура назначение redirect, доступность видимой формы и реальные поля. Неверный бренд, Disabled, requires_access и отсутствующая tracking URL — отдельные блокировки, не успешные пресеты.
3. Выбирать отдельного ещё не отправленного лида admin из таблицы по смыслу его вакансии. Проверить историю по телефону и всем canonical aliases. SMM не становится курьером; сборщик не становится продавцом-кассиром. Изменение тестового названия не разрешает повтор.
4. Проверить обязательные поля именно этой формы. Не требовать резюме там, где его нет, но не придумывать дату рождения, город, гражданство, транспорт или готовность к самозанятости. Если подходящего полного лида нет, фиксировать `no_eligible_candidate`; тест обработки данных выполнять отдельно без кандидатского POST.
5. Контрольная отправка выполняется в ограниченном owner-scoped job/lease с heartbeat, обычной записью результата и защиты от повторов. Не менять постоянно отключённые офферы пользователя ради теста и не запускать весь цикл вместо одной проверки.
6. Перед единственным submit проверить видимую форму и нормализованные значения. Не повторять при неопределённом исходе; сначала сверить endpoint, success-state и историю.
7. Для каждого успешного пресета сохранить реальный экран «Спасибо»/принятой анкеты, timestamp, endpoint/status, роль, owner и runtime revision. Для недоступного сохранить экран/ответ причины. Данные кандидата и секреты не публиковать в GitHub; скриншот должен скрывать поля кандидата без изменения текста подтверждения.
8. В отчёте разделять: доступность формы; заполнение до submit; изолированный тест с mock; реальный приём endpoint; подтверждённую атрибуцию. Mock и исторический screenshot никогда не выдавать за сегодняшнюю реальную отправку.
9. Результаты всех пресетов оформлять матрицей без пропусков. Открытие формы, 2xx без success-state или статический текст «Спасибо» не означает успешной доставки. Недоступные/неподходящие пресеты нельзя объявлять рабочими. Один контроль не отменяет правило трёх последовательных успехов для стабилизации.

Текущие доказательства и ограничения: [[Offer Presets]]. Полный отчёт проверки хранить с датой; изменившуюся ссылку/роль/форму проверять заново.


Дополнение по прямому указанию пользователя 09.10 «проверь любым кандидатом»: для ограниченной контрольной заявки допускается выбрать другого полного лида из таблицы, даже если название исходной вакансии отличается.
