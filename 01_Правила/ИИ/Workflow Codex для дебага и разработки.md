# Workflow Codex для дебага и разработки

Канонический workflow работы Codex с TrafficHub. Проверен: 2026-10-08. Operational-правила `AGENTS.md` имеют приоритет при конфликте.

## Источники истины

- Факты: проверенные код, runtime, БД, env, контейнеры, логи, state-файлы и реальные серверные артефакты.
- Wiki, документация, старые заметки и устные договорённости — ориентир, не доказательство.
- Неподтверждённый вывод явно помечай как гипотезу.
- Канонический product repo: `/root/TrafficHub` на сервере. `/app` в контейнере — runtime-доказательство, не repo.
- Локальные product-клоны не создавать.

## Режим и риск

Перед работой назвать режим и риск.

1. `fix`, `read-only` или `low-risk`: подтвердить симптом, локализовать причину, сделать одну изолированную правку и целевую проверку. Не менять данные, контейнеры, toggles или maintenance mode без необходимости.
2. `release`, `runtime-risk`: изолированная правка в server repo/worktree; по правилу 2026-10-08 выполнить локальные целевые проверки, прямой deploy и live smoke без обязательного GitHub-круга. Если пользователь уже поручил исправление и релиз, обычные шаги release не требуют повторного вопроса.
3. `incident`, `runtime-risk` или `data-risk`: сначала минимально ограничить impact, затем восстановить наблюдаемость, зафиксировать evidence и только потом исправлять. Массовая запись/удаление, миграция и остановка критичных сервисов требуют отдельного подтверждения.

Если риск неясен, считать его `runtime-risk` до проверки.

## Субагенты

Для узкой задачи достаточно основного агента. Делегировать только независимую
подзадачу или отдельную проверку, когда это помогает качеству; наличие четырёх
ролей не требует четырёх запусков. При делегировании роли: Обзорщик,
Планировщик, Разработчик, Валидатор; основной агент отвечает за scope и state.
Модели выбирать из доступных с учётом сложности; исторические Terra/Sol не
требуют запуска отсутствующих моделей. Субагент не расширяет полномочия.

Обычная порученная правка выпускается напрямую по production-контуру ниже.
Отдельное разрешение требуется для деструктивных действий, миграций, массовых
записей, остановки критичных сервисов и включения maintenance.

## Evidence-card

Для каждой задачи, которая меняет код, runtime или данные, завести короткую evidence-card рядом с задачей или PR:

```text
Симптом:
Scope и owner/tenant:
Baseline SHA и runtime:
Причина (доказательство):
Изменение:
Проверки:
Live evidence:
Rollback:
Residual risks:
```

Graphify использовать только для навигации по актуальному snapshot. Доказательством служат code/runtime/DB/logs, а не граф.

## Рабочий цикл

`Контекст — Воспроизведение — Диагноз — Изолированная правка — Проверка — Готово к релизу — Deploy в разрешённом контуре — Live smoke — Документация`.

Перед изменением зафиксировать: симптом, время, шаги воспроизведения, owner без секретов и лишних ПДн, correlation/job ID или endpoint, expected/actual, `git status -sb`, ветку, commit и состояние затронутых контейнеров.

Локализовать затронутую подсистему. Для известной зоны использовать `rg`; для незнакомой или сложной трассировки — Graphify. Проверять одну гипотезу самым узким достаточным read-only сигналом. Не делать широких проверок без связи с изменением.

## Production guardrails

- Для live использовать SSH alias `traffichub-live` и principal `codex`.
- Сложный Bash передавать через `scripts/ssh_live_bash.ps1`.
- Не редактировать `/app` или mutable-слой контейнера.
- Maintenance mode, stop worker/scheduler, toggles, миграции, массовая запись и удаление требуют явного разрешения.
- Перед `runtime-risk`/`data-risk` действием определить точную цель, backup или snapshot, affected rows и rollback path.
- Не использовать `git reset --hard` как штатный rollback.

## Проверки по зоне

- Frontend: lint/build, целевой UI-сценарий, visual/browser smoke, новый asset.
- API/backend: targeted test, контракт endpoint, негативный сценарий.
- Auth/settings: admin, обычный user, запрет доступа к чужому tenant.
- Worker/queue/scheduler: состояния, retry, idempotency, owner scope.
- Интеграция: normal response, timeout/error, отсутствие каскадного падения.
- DB/миграция: backup, dry run при возможности, affected rows, rollback probe.
- Deploy: локальный ожидаемый commit, состояние затронутого сервиса, health, логи, smoke сценария. GitHub checks — только при отдельно выбранном GitHub-контуре.

После изменения выполнить `git diff --check` и только релевантные проверки. Для UI сравнить с референсом; при отсутствии эффекта сначала доказать stale container, mount, build cache, CDN или cache-busting.

До `release` и при `incident` запустить `deploy/doctor.sh`: SSH, Git, Docker/Compose, доступность Graphify, свободное место/inodes и health. `doctor` не заменяет release-status и smoke.

## Wiki

Raw-источники неизменяемы. Wiki — производный слой; не копировать в неё секреты, ПДн, изменяемые runtime-артефакты и полные логи.

Wiki обновлять только при устойчивом подтверждённом знании: архитектурное решение, новое эксплуатационное правило, повторяемый баг или значимое изменение поведения. Обновлять один канонический узел, связывать Markdown-ссылками, указывать дату проверки и источник доказательства. Для новой точки входа обновлять `[[00_Главное/Index]]` и `[[00_Главное/Главная/История изменений]]`.

## Завершение

`Готово к релизу`: причина подтверждена, правка изолирована, `git diff --check` и релевантные проверки зелёные, diff и rollback понятны.

`Развёрнуто и проверено`: пользователь поручил правку на проде; `/root/TrafficHub` содержит локальный ожидаемый commit, целевые проверки и deploy/health/live smoke успешны. По правилу 2026-10-08 push и GitHub checks нужны только при отдельном запросе GitHub-контура.

В отчёте: подтверждённые факты, гипотезы, изменения, выполненные точные команды проверок, результат, wiki-изменения, разумный следующий шаг.


## Прямой production-контур — 2026-10-08

По прямому указанию пользователя «делай сразу на прод без гит хаба» и «сделай это за канонической правило» обычные правки TrafficHub по умолчанию выполнять и выпускать непосредственно из канонического серверного репозитория `/root/TrafficHub`, без обязательных push, PR, merge через GitHub или ожидания GitHub Actions. GitHub-синхронизация и GitHub release используются только по отдельному запросу пользователя.

Это указание отменяет прежние обязательные GitHub-gates workflow для такого прямого контура. Сохраняются: узкая изолированная правка, фиксация локального server commit и diff, целевые проверки, rollback, пересоздание только затронутых сервисов при необходимости, runtime/live smoke и обновление канонической `baza`. Не редактировать mutable `/app` контейнера. Для UI проверять браузер, темы, responsive и доступность. Полный набор тестов — только по явному запросу. Деструктивные действия и изменения данных не становятся разрешёнными автоматически.

## Короткий маршрут и актуальность proof — 2026-10-08

Одна узкая задача: scope/риск/критерий успеха → пакет доказательств → минимальная
правка → целевая проверка → разрешённый выпуск при необходимости → знания.
Harness stages сохраняются; FIX/SHIP без применимого действия отмечаются как
no-op в history. Optional tools, дополнительные агенты и полный suite не
становятся обязательными из-за наличия в checklist.

Перед итоговыми receipts вызывать `bind_proof_revision(workstream, repo, paths)`
для всех релевантных проверенных файлов. Передавать полученный `proof_revision`
в `make_receipt`, а `proof_repo=repo` в `transition(..., CLOSED, ...)`.
CLOSED перечитывает файлы и отвергает изменённые/пропавшие исходники, чужие,
устаревшие, повреждённые и неуспешные receipts. После новой правки нужны повторная
привязка и затронутые проверки. Старые открытые задачи требуют новой проверки;
исторические закрытые записи не переписываются.

Hash подтверждает согласованность содержимого, а не запуск команды. Evidence
должен описывать исходный сценарий, фактический вывод проверок и, для runtime,
развёрнутую версию и live smoke. Доказательства проверки 2026-10-08:
