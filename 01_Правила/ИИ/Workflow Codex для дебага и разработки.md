# Workflow Codex для дебага и разработки

Канонический workflow работы Codex с TrafficHub. Проверен: 2026-07-29. Operational-правила `AGENTS.md` имеют приоритет при конфликте.

## Источники истины

- Факты: проверенные код, runtime, БД, env, контейнеры, логи, state-файлы и реальные серверные артефакты.
- Wiki, документация, старые заметки и устные договорённости — ориентир, не доказательство.
- Неподтверждённый вывод явно помечай как гипотезу.
- Канонический product repo: `/root/TrafficHub` на сервере. `/app` в контейнере — runtime-доказательство, не repo.
- Локальные product-клоны не создавать.

## Режим и риск

Перед работой назвать режим и риск.

1. `fix`, `read-only` или `low-risk`: подтвердить симптом, локализовать причину, сделать одну изолированную правку и целевую проверку. Не менять данные, контейнеры, toggles или maintenance mode без необходимости.
2. `release`, `runtime-risk`: отдельная ветка и server worktree; после зелёных checks выполнить merge, deploy и live smoke. Если пользователь уже поручил исправление и релиз, обычные шаги release не требуют повторного вопроса.
3. `incident`, `runtime-risk` или `data-risk`: сначала минимально ограничить impact, затем восстановить наблюдаемость, зафиксировать evidence и только потом исправлять. Массовая запись/удаление, миграция и остановка критичных сервисов требуют отдельного подтверждения.

Если риск неясен, считать его `runtime-risk` до проверки.

## Субагенты

По умолчанию делить нетривиальную задачу между role-agent'ами:

1. `Исследование`: только `read-only`; фиксирует symptom/reproduction, факты отдельно от гипотез, scope, evidence и безопасный handoff.
2. `Разработка`: отдельная branch/worktree; делает одну минимальную изолированную правку и целевые проверки; передаёт статус только `Готово к релизу`.
3. `Релиз`: действует только после явного разрешения пользователя; проверяет main SHA, GitHub checks, backup/rollback, deploy, health, логи и live smoke.

Основной агент координирует handoff `Исследование → Разработка → Релиз`, собирает доказательства и принимает финальное решение. Не создавать subagent для одношагового read-only ответа или правки без независимой подзадачи.

Subagent не расширяет полномочия: режим, риск, production guardrails и явное release-разрешение обязательны для каждого.

## Evidence-card

Для каждой задачи, которая меняет код, runtime или данные, завести короткую evidence-card рядом с задачей или PR:

```text
Симптом:
Scope и owner/tenant:
Baseline SHA и runtime:
Причина (доказательство):
Изменение:
Проверки:
Live evidence:
Rollback:
Residual risks:
```

Graphify использовать только для навигации по актуальному snapshot. Доказательством служат code/runtime/DB/logs, а не граф.

## Рабочий цикл

`Контекст — Воспроизведение — Диагноз — Изолированная правка — Проверка — Готово к релизу — Разрешённый deploy — Live smoke — Документация`.

Перед изменением зафиксировать: симптом, время, шаги воспроизведения, owner без секретов и лишних ПДн, correlation/job ID или endpoint, expected/actual, `git status -sb`, ветку, commit и состояние затронутых контейнеров.

Локализовать затронутую подсистему. Для известной зоны использовать `rg`; для незнакомой или сложной трассировки — Graphify. Проверять одну гипотезу самым узким достаточным read-only сигналом. Не делать широких проверок без связи с изменением.

## Production guardrails

- Для live использовать SSH alias `traffichub-live` и principal `codex`.
- Сложный Bash передавать через `scripts/ssh_live_bash.ps1`.
- Не редактировать `/app` или mutable-слой контейнера.
- Maintenance mode, stop worker/scheduler, toggles, миграции, массовая запись и удаление требуют явного разрешения.
- Перед `runtime-risk`/`data-risk` действием определить точную цель, backup или snapshot, affected rows и rollback path.
- Не использовать `git reset --hard` как штатный rollback.

## Проверки по зоне

- Frontend: lint/build, целевой UI-сценарий, visual/browser smoke, новый asset.
- API/backend: targeted test, контракт endpoint, негативный сценарий.
- Auth/settings: admin, обычный user, запрет доступа к чужому tenant.
- Worker/queue/scheduler: состояния, retry, idempotency, owner scope.
- Интеграция: normal response, timeout/error, отсутствие каскадного падения.
- DB/миграция: backup, dry run при возможности, affected rows, rollback probe.
- Deploy: ожидаемый commit, GitHub checks, Compose status, health, логи, smoke затронутого сценария.

После изменения выполнить `git diff --check` и только релевантные проверки. Для UI сравнить с референсом; при отсутствии эффекта сначала доказать stale container, mount, build cache, CDN или cache-busting.

До `release` и при `incident` запустить `deploy/doctor.sh`: SSH, Git, Docker/Compose, доступность Graphify, свободное место/inodes и health. `doctor` не заменяет release-status и smoke.

## Wiki

Raw-источники неизменяемы. Wiki — производный слой; не копировать в неё секреты, ПДн, изменяемые runtime-артефакты и полные логи.

Wiki обновлять только при устойчивом подтверждённом знании: архитектурное решение, новое эксплуатационное правило, повторяемый баг или значимое изменение поведения. Обновлять один канонический узел, связывать Markdown-ссылками, указывать дату проверки и источник доказательства. Для новой точки входа обновлять `[[00_Главное/Index]]` и `[[00_Главное/Главная/История изменений]]`.

## Завершение

`Готово к релизу`: причина подтверждена, правка изолирована, `git diff --check` и релевантные проверки зелёные, diff и rollback понятны.

`Развёрнуто и проверено`: пользователь разрешил релиз; commit запушен, checks зелёные, `/root/TrafficHub` содержит ожидаемый commit, deploy/health/live smoke успешны.

В отчёте: подтверждённые факты, гипотезы, изменения, выполненные точные команды проверок, результат, wiki-изменения, разумный следующий шаг.
