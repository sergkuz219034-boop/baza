# Fast debug loop

Теги: #плейбук #debug #workflow

## Назначение

Минимальный рабочий цикл для повторяющихся багов в TrafServer / TrafficHub, когда нужно быстро понять причину, внести точечную правку и подтвердить результат на live runtime.

## Принцип

Один проход должен отвечать на три вопроса:

1. что именно сломано;
2. где это живёт в коде или runtime;
3. как быстро подтвердить исправление.

Если ответов больше, чем нужно для текущего бага, цикл уже слишком тяжёлый.

## Быстрый цикл

1. Зафиксировать симптом одной фразой.
2. Определить одну зону системы.
3. Проверить только нужный live-сигнал:
   - лог;
   - health;
   - конкретный endpoint;
   - конкретный контейнер;
   - конкретный тест.
4. Открыть только те файлы, которые реально участвуют в потоке ошибки.
5. Внести минимальную правку на сервере.
6. Прогнать один targeted test или один live smoke, а не весь suite.
7. Если runtime менялся, пересобрать только затронутый контейнер.
8. Подтвердить на live-логе или endpoint.
9. Закоммитить и запушить серверный repo.
10. Сразу синхронизировать wiki.

## Что ускоряет работу

- Не держать локальный app clone.
- Работать только в `/root/TrafficHub`.
- Для проверки брать не “все логи”, а один релевантный tail.
- Для теста брать не “весь pytest”, а самый узкий доступный набор.
- При повторяющихся инцидентах использовать уже существующие заметки `03_Ошибки/Расследования` и `01_Правила/Решения`, а не пересобирать картину заново.

## Что замедляет работу

- широкий repo scan без гипотезы;
- запуск всего тестового набора без необходимости;
- правка нескольких подсистем за один проход;
- откладывание wiki-sync до конца длинной серии правок;
- попытка чинить live-only баг без проверки контейнера и логов.

## Практическое правило

Если можно проверить гипотезу за один targeted test или один live smoke, не расширяй проверку заранее.
