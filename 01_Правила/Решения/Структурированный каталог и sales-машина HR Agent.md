# Структурированный каталог и sales-машина HR Agent

## Проблема

Факты вакансий, порядок вопросов и переход к анкете одновременно хранились в промте и Markdown. Из-за конфликтов LLM смешивала офферы, повторяла этапы и ошибочно заполняла поля свободным вопросом кандидата.

## Контекст

Telegram Business webhook должен отвечать быстро и предсказуемо, сохраняя естественную речь рекрутера. Условия и ссылки меняются через AccountManager и принадлежат owner-scoped binding.

## Решение

- Каталог вакансий хранится в `hr_agent_vacancies`; стабильный ключ — `prompt_profile.offer_code`.
- `offer_catalog.py` создаёт/нормализует шесть канонических офферов в scope `tenant_id + owner_username`.
- `sales_engine.py` отвечает за обязательный анализ, выбор первого Onecta, маршрутизацию альтернатив, согласие на внешнюю анкету, стоп-сигналы и статусы.
- `service.py` оставляет LLM формулировку вопросов и возражений, но передаёт ей только выбранную вакансию и защищённые правила.
- Markdown хранит технику продаж; системный промт хранит женскую персону и запреты; факты из них удаляются.
- Dashboard редактирует структурированные поля вакансии и показывает извлечённый state кандидата.
- OpenRouter является основным генератором финальной реплики и follow-up. В контекст входят системный промт binding, Markdown-база, выбранная структурированная вакансия, история, state, temperature, dialog variability и безопасный черновик sales-машины.
- `_validate_generated_reply()` оставляет за кодом последнюю границу: отклоняет повтор прошлой реплики, запрещённый сбор данных, неизвестные URL и потерю обязательной ссылки. При отказе guardrail или ошибке провайдера используется детерминированный черновик.

## Последствия

- Условия разных вакансий не смешиваются.
- Ссылку можно отправить один раз после явного согласия и повторить только по просьбе.
- Вопрос имеет приоритет над продвижением этапа.
- Изменение фактов требует правки карточки вакансии, а не prompt engineering.
- Старые кандидаты требуют одноразовой очистки legacy state с сохранением `hr_agent_messages`.
- Служебная команда `/clear` сбрасывает активное состояние кандидата и разговора, отменяет pending touches и возвращает этап `greeting`. История `hr_agent_messages` намеренно не удаляется: она нужна для аудита и дедупликации, а Telegram Business connection сохраняется для дальнейшей доставки.
- `extra_config.dialog_variability` конкретного binding принимает `0..3`: уровень ограничивает число доступных формулировок приветствия и презентации, а счётчики `_variant_*` не очищаются командой `/clear`. LLM `temperature` остаётся отдельной настройкой.
- Неоднозначный естественный текст классифицируется `_semantic_intent()` по полной реплике, этапу, предыдущим сообщениям и `answered_fields`. Классификатор возвращает только enum-намерение; выбор оффера, изменение state и финальный ответ остаются в `sales_engine.py`. При ошибке или недоступности провайдера intent равен `unknown`, после чего работает детерминированный fallback.

## Альтернативы

- Только системный промт: отклонено из-за недетерминированных переходов и конфликтов фактов.
- Отдельная жёсткая машина для каждого оффера: отклонено из-за дублирования; общий движок использует routing metadata каталога.
