# 2026-07-10 Short activation key format

## Симптом

`KEY.exe` генерировал длинные activation keys, которые неудобно передавать клиентам.

## Проверка

- Длина RSA-подписи остаётся неизменной; сокращать её означало бы ослабить защиту.
- Основной размер занимал base64-представленный JSON payload.
- Server verifier, `ActivateLicense.exe` и GUI keygen проверены по одному формату.

## Решение

- Основной формат для новых ключей: `TH3-xxxxxxxxxxxxxxxx` - серверный код длиной 20 символов.
- `KEY.exe` сначала создаёт подписанный `TH2.payload.signature`, затем передаёт его на `POST https://traffic-hub.pro/license/shorten`.
- `license_server` проверяет подпись, сохраняет связку `TH3 -> TH2` в PostgreSQL (`license_short_keys`) и возвращает короткий код.
- При активации приложение и Operator CRM получают исходный `TH2` через `GET /license/resolve/{TH3}`, после чего повторно проверяют подпись локально. Короткий код не заменяет криптографическую проверку.
- Для активации `TH3` требуется доступ к `traffic-hub.pro`. Если выдача короткого кода в keygen недоступна, он оставляет полный `TH2` вместо создания невалидного ключа.
- `TH1` и `TH2` остаются совместимыми со старыми и офлайн-сценариями.
- Новый `KEY.exe` собран локально из server source; keygen не входит в публичные releases.

## Проверка после изменений

- `tests/test_license_key_security.py` и `tests/test_activate_license.py`: `9 passed`.
- Live-проверка: `TH3-Xck3fwBFzRqMLnEW` (тестовый код) раскрылся в исходный `TH2`; основной verifier подтвердил login и роль `operator`.
- Длина проверенного тестового `TH2`: 581 символ, `TH3`: 20 символов.
- Live app rebuilt; `/api/health` возвращает `status=ok`.

## Регрессия GUI и исправление

### Симптом

После нажатия `Сгенерировать` локальный `KEY.exe` переставал отвечать и не создавал запись в `license_short_keys`.

### Проверка

- Процесс запускался и показывал PIN-форму, поэтому сборка и Windows launcher были исправны.
- Во время зависания `license_server` не получал `POST /shorten`; сбой происходил до API.
- Прямой запрос с той же Windows-машины к endpoint отвечал штатно.

### Вывод

Синхронный `.NET WebClient` использовал устаревшие TLS-настройки и системный proxy без ограничения времени ожидания. Сетевое ожидание выполнялось в UI-потоке и замораживало форму.

### Исправление

- Для служебного запроса включён TLS 1.2.
- Системный proxy отключён только для вызова `traffic-hub.pro/license/shorten`.
- Добавлены connect/read-write таймауты 10 секунд; при недоступности сервиса сохраняется совместимый `TH2` fallback.
- Новая локальная сборка проверена через реальный GUI: окно осталось отзывчивым, создан `TH3` длиной 20 символов, server verifier подтвердил роль `operator` и наличие пароля.

## Производительность интерфейса

### Симптом

Кнопки `Сгенерировать` и `Сохранить в файл` ощущались медленными, а сообщения журнала появлялись по одной строке и визуально исчезали.

### Вывод

`RequestShortKey` и запись файла выполнялись синхронно в UI-потоке. Кроме этого журнал имел высоту 20 пикселей: фактически пользователь видел только последнюю строку.

### Исправление

- Генерация короткого ключа и сохранение файла перенесены в фоновую задачу; окно остаётся доступным для перерисовки и не зависает во время сети или OneDrive-синхронизации.
- Во время операции на кнопке показывается `Создаю...` или `Сохраняю...`; повторные нажатия заблокированы до завершения.
- Журнал расширен до прокручиваемого блока и автоматически остаётся на последнем сообщении.
- Проверка реального GUI подтвердила: ключ `TH3` получен, кнопки снова активны, последние три сообщения журнала остаются видимыми.

## Уникальные файлы ключей

`Сохранить в файл` больше не использует постоянное имя `license_web-register.txt`. Новый файл создаётся в папке `KEY.exe` в формате `license_<роль>_YYYYMMDD_HHMMSS_mmm_<случайный-суффикс>.txt` и открывается в режиме `CreateNew`. При совпадении имени генератор выбирает другое, не перезаписывая существующий ключ.
